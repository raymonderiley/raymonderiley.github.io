We Have Two Different RTOs? Who Thought of This Bright Idea?


The Meeting Where Everyone Groans

Tell a room of application owners that their critical system now has two recovery time objectives, and you can watch the eye-rolls happen in real time. One RTO was hard enough to get signed off. Why would anyone want a second one?

Because the first one was written for a different kind of bad day.

Most recovery targets were set with a "normal" disaster in mind: a storage array fails, a data center loses power, a cloud region goes dark. In those events, replication is the hero. A copy of the application and its data is already running somewhere else, and we fail over to it. That is fast, it is tested, and it works.

Ransomware and large-scale destructive malware break that model. Replication is designed to copy every change from the primary to the secondary as quickly as possible. It does not know the difference between a legitimate transaction and an attacker encrypting your database. In a cyber event, the replica faithfully receives the damage too. You fail over, and you land on the same broken data.

So the honest answer to "who thought of this bright idea?" is: the attackers did. We are just writing it down.


Two Clocks, Two Recovery Paths

A mature continuity program carries two recovery targets for every critical application:


  Operational RTO (the "normal disaster" clock):
How long it takes to recover when the infrastructure fails but the data can be trusted. Recovery uses replication, failover to a secondary site or cloud region, or standby capacity. This is usually measured in minutes or hours.
  Cyber RTO (the "we can't trust anything" clock):
How long it takes to recover when the replicated copies cannot be used because they are encrypted, corrupted or simply untrusted. Recovery comes from protected backups, restored into a clean environment, checked for integrity and brought back in a controlled order. This is usually measured in days, and the first honest measurement often surprises people.


The same thinking applies to recovery point objectives. With replication, the data loss window can be close to zero. In a cyber event, the recovery point is the last backup you can prove is clean, which may be hours, days or even weeks old if the attacker was inside for a while. If the business wants the cyber RPO to match the operational RPO, that is possible, but it costs money: more frequent protected backups, longer retention, more storage and more scanning.


  The Technical View:
Replication protects availability. Backups protect recoverability. On-premises, that means storage and virtual machine replication cannot be the only plan. In the cloud, cross-region replication, read replicas and snapshots kept in the same account as production all share the same weakness. In SaaS, sync tools and connectors can push bad changes everywhere at once. Every environment needs an isolated, immutable copy that the attacker cannot reach with production credentials.
  Leadership Translation:
We are not admitting failure by publishing a longer cyber RTO. We are telling the truth about how long recovery takes when the threat is an attacker instead of a power outage. A single, optimistic RTO that only covers the easy scenario is the bigger risk, because the business will make promises to customers it cannot keep.

Backups Become the Recovery Path, So Measure Them Like One

For years, backup teams were measured on whether the job finished overnight. In a cyber event, the questions change: how fast can we read the data back, how much can we restore at the same time, and where can we restore it safely?

That makes backup infrastructure a recovery system, not an insurance policy sitting on a shelf. The cyber RTO is set by the slowest link in a long chain:


Storage read speed: Backup storage is usually tuned to save space, not to read data back quickly. Restores are often much slower than backups.
Network throughput: Terabytes have to travel from the backup repository to the recovery environment. The pipe between them can be the real bottleneck.
Concurrency: Restoring one application in a test is very different from restoring fifty at once while everyone competes for the same storage and bandwidth.
Clean environment: Identity services, DNS and core networking often have to be rebuilt first, in an isolated space, before any application can come back.
Validation: Restored data has to be scanned and checked by the application owner before anyone trusts it.

A simple example shows why this matters. An application with 40 TB of data and a restore path that sustains 2 TB per hour needs about 20 hours just to move the data. That is before rebuilding identity, scanning for malware or letting the business confirm the data is correct. If that application's only RTO says eight hours, the plan is fiction.

The only way to know the real number is to test it. Every critical application needs a baseline restore test from protected backups into an isolated environment, with the results written down: data volume, restore throughput, time to first usable system, time to validated business service. That baseline becomes the starting point for the cyber RTO.

And because storage and networks change all the time, the baseline does not stay true forever. Data grows. Applications move to the cloud. Network links get upgraded or shared with new workloads. The baseline has to be re-measured on a schedule and whenever the architecture changes, so the cyber RTO keeps matching reality.


Expanding the DR Program to Carry Both Clocks

This is not a new program. It is the existing disaster recovery program growing up. In practice, that means:


Define both targets in the BIA: Every critical application gets an operational RTO/RPO and a cyber RTO/RPO, each with a business owner who has signed off on it.
Add cyber recovery testing to the test calendar: Failover tests prove the operational clock. Restore-from-backup tests in an isolated environment prove the cyber clock.
Treat backup infrastructure as recovery capacity: Measure storage and network throughput for restores, track it over time and plan capacity for a mass-restore event, not just nightly jobs.
Agree on a restore order: Decide in advance which services come back first in a cyber event, starting with the foundations everything else depends on.
Report the gap honestly: Where the tested cyber RTO is longer than the business can tolerate, leadership chooses: fund the fix, change the design or formally accept the risk.


Getting Application Owners on Board Without a Mandate

None of this works without application owners, and most DR teams have no authority over them. This is exactly where the principles from my earlier post, Leading Without a Title, earn their keep. A short version:


Start with their pain, not your program: Ask what keeps the team from hitting its targets this quarter. Many owners already suspect their recovery plan would not survive ransomware. Offer to help them find out before an auditor or attacker does.
Speak each audience's language: Engineers want less toil, so bring a ready-made restore test and a template, not a policy document. Business owners care about revenue and customers, so frame the cyber RTO as protecting both. Executives think in risk and options, so bring the measured gap, the cost to close it and a recommendation.
Bank goodwill before you need it: Build relationships with application teams long before the first test window or audit request.
Pre-wire the big decisions: Meet key owners one on one before a governance review, so the two-RTO standard arrives with support already in the room.
Give credit loudly: When an application team completes its first baseline restore, make sure their leadership hears about it.

Influence turns the two-RTO conversation from "another compliance ask" into "we found out the truth together, and now we can fix it.". You can also use this opportunity to ask "is there a chance we can bring this application up as some sort of minimum viable service while the full restore is happening?". That can potentially shorten the cyber RTO for the business without changing the underlying recovery path. It then becomes a win-win for the application team, the DR team and the business!


Write It Down Where Everyone Can Find It

Everything learned from application owners should live in one standardized place: the application inventory or CMDB the enterprise already uses, such as an enterprise architecture tool like SAP LeanIX. Scattered spreadsheets and slide decks do not survive a crisis or an audit.

For each application, record at least:


Business owner, technical owner and criticality tier.
Operational RTO/RPO and cyber RTO/RPO, with the date each was approved.
Hosting model (on-premises, cloud infrastructure, cloud platform or SaaS) and recovery method for each clock.
Data volume, backup frequency, retention and whether a protected, isolated copy exists.
Last baseline restore result: throughput, time to first system, time to validated service.
Upstream and downstream dependencies, and the restore order position.
Open gaps, risk acceptances and the next test date.

When this lives in the application CMDB, it stops being "the DR team's data." It becomes part of how the enterprise describes its own applications, and it is there when an incident commander needs it at 3 a.m.


Automate It, or It Will Drift

Everything above can be done by hand for a pilot of five or six applications. It cannot be done by hand for hundreds, and it cannot stay accurate by hand for long. People change roles, spreadsheets go stale, a test gets skipped during a busy quarter and nobody notices until the auditor or the attacker does. Manual programs do not fail all at once. They drift, quietly, until the numbers in the CMDB describe an environment that no longer exists.

Automation is what turns a good idea into a program that holds up. The goal is simple: make the right thing happen by default, and make the wrong thing visible immediately.


Scheduled restore tests: Baseline restores from protected backups into an isolated environment run on a calendar set by each application's tier, without someone having to remember to book them.
Measurements captured, not typed: Data volume, restore throughput, storage read rate, network throughput and time to a working system are pulled straight from the backup platform and test tooling. Nobody copies numbers into a form.
The CMDB updates itself: Test results flow into the application record through an integration, so the cyber RTO on file always reflects the most recent test, with its date.
Change triggers a re-baseline: When a change ticket touches storage, networking, a cloud migration or a large data growth threshold, the affected applications are automatically flagged for a new baseline test.
Drift detection: Automated checks look for the gaps that creep in: a new application with no protected backup, cloud snapshots stored in the same account as production, a SaaS platform with no copy outside the vendor, or a backup retention policy that was quietly shortened.
Recovery as code: The clean recovery environment and the restore order are defined as code and runbooks that can be launched the same way every time, in a test or a real event. A process that only lives in one engineer's head is not a process.
Alerts and reporting: Expired baselines, failed restores and widening gaps between target and tested cyber RTO show up on a dashboard and in alerts to the owner, not in a report six months later.


  The Technical View:
Automation removes the toil that makes application teams resist the program. Instead of asking them to run tests and fill in forms, the program hands them results. That is the strongest form of influence there is: make participation the easy path.
  Leadership Translation:
Automated evidence is trustworthy evidence. When leadership, auditors or regulators ask whether a critical application can recover from ransomware, the answer comes from a test that ran last month, not a plan someone wrote last year.

One caution. Automation should make recovery more reliable, not create a new way to destroy it. Anything that can delete backups, shorten retention or change immutability settings should never run without a human approval and separate credentials. Automate the measuring, testing and reporting freely. Keep humans firmly in charge of anything destructive.  Of course, the recovery process can refined/tuned over time, thus only get better with each iteration!

No program is truly foolproof, but an automated one comes close. It keeps measuring when people are busy, notices change when nobody announces it, and keeps both recovery clocks honest long after the first pilot is finished.


The Bottom Line

Two RTOs are not bureaucracy. They are an admission that a broken server and a hostile attacker are different problems with different recovery paths. Replication will get you through the first. Only tested, protected, measured backups will get you through the second.

The organizations that recover from ransomware in days instead of weeks are not lucky. They measured their cyber clock before they needed it, kept the measurement current as their storage and networks changed, and brought their application owners along through influence rather than mandate.

So yes, we have two different RTOs. It was a bright idea after all!
