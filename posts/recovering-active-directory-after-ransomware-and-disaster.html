Recovering Active Directory After Ransomware and Disaster

Blog | Active Directory Recovery

If you have ever lost a badge and found that every door, printer and laptop in the building stopped trusting you at once, you have a small idea of what happens when Active Directory goes down. Active Directory is the system most large companies use to answer one question for every person, server and application: who are you, and what are you allowed to do? When it is unavailable, the answer to every one of those questions becomes no. When it is compromised, the answer becomes dangerously unreliable. This post explains what recovery really takes, how the steps differ for a disaster, ransomware or a state-level adversary, and why applications and Active Directory depend on each other in ways that often surprise teams in the middle of an incident.

Part A: What a Recovery Needs to Know and Do

The pieces that matter

A recovery team needs to understand a short list of things. The forest is the outer boundary, and it contains one or more domains. Each domain has domain controllers, the servers that hold a copy of the directory and answer sign-in requests. Five special roles, called operations masters, are held by specific domain controllers. DNS lets computers find domain controllers. SYSVOL carries policy files. A secret called krbtgt signs every Kerberos ticket, so whoever holds it can forge identity. Trusts between domains and forests let identity cross boundaries. Finally, backups have a life: a backup older than the tombstone lifetime, 180 days by default in current forests, can reintroduce deleted objects and break replication.

A good plan also names what is not in the directory but is needed to rebuild it: an offline inventory of domains and domain controllers, sealed local credentials for hypervisors and backup, clean installation media and an isolated network to restore into.

Recovering from a disaster

A disaster is a failure without an attacker: storage loss, a site outage, corrupt replication or a bad change. The backups are trustworthy, so speed and accuracy matter most. If a healthy domain controller still exists in each domain, the better path is often to seize its roles and add new domain controllers. A full forest recovery is the last resort, used when no healthy domain controller remains or when corruption has spread to all of them.

  1. Isolate the remaining domain controllers from the network so they cannot replicate unwanted data into the restored directory.
  2. Record the forest structure, the role holders and the backup dates, and choose the newest backup within the tombstone lifetime for one writable domain controller in each domain.
  3. Restore the forest root domain first, then each child domain, into an isolated network in directory services restore mode, without restoring the other domain controllers.
  4. On each restored domain controller, seize all five operations master roles, remove the metadata of every domain controller that was not restored, raise the available RID pool, reset the domain controller's own computer account password and make it a DNS server and global catalog.
  5. Fix time, with the PDC emulator taking time from a reliable source, and confirm DNS service records.
  6. Rebuild the remaining domain controllers by installing clean servers and promoting them, using install-from-media for large domains.
  7. Validate replication, SYSVOL, Kerberos and sign-in with a small group, then reconnect by site and return applications in tiers.

Recovering from ransomware

Ransomware changes one thing: trust. The attacker usually holds privileged credentials, has often copied the directory database and may have destroyed or poisoned the backups. Every step above still applies, but each one needs proof. A backup is a hypothesis until it has been shown to predate the intrusion and scanned in isolation. The recovery hosts, the backup platform and the administrators' workstations must be clean before any restore begins.

  • Prove the restore point. Find the earliest evidence of attacker activity and choose a backup before it, even if it costs lost changes.
  • Reset more than krbtgt. Reset krbtgt twice, with enough time between resets for replication and for the maximum ticket lifetime, and also reset trust passwords, domain controller computer accounts, privileged and service account secrets and the directory services restore mode password.
  • Remove what the attacker left in the directory: changes to the template that protects privileged accounts, delegated permissions, Group Policy edits, certificate templates, added keys on accounts and forged identity history.
  • Rebuild what is adjacent: certificate authorities, federation, directory synchronization, backup and management tools. Restore only what you must, and rebuild everything else.
  • Release users in waves with strong verification, because impersonating the help desk is a common second attack.

Recovering from a state-level adversary

A patient adversary may have been present for months, with footholds in cloud identity, hypervisors, firmware and suppliers. Here the safest assumption is that the old forest cannot be cleaned. The plan leans toward a rebuild: new or verified hardware, a new network, new certificate authorities, new administrative accounts and new secrets, with users and groups migrated selectively and without carrying over identity history or old credentials. The old forest is kept disconnected for forensics. Communication, authentication and approval use channels that were never connected to the old directory, government and legal contacts are involved early, and threat hunting continues for months with a defined trigger to rebuild again if the adversary returns.

For Sr. Leadership, the decision is not technical. It is a choice among three options: clean up in place, restore from a clean backup or rebuild. Each has a different time to first sign-in, cost and risk of reinfection, and the playbook should show those side by side before an incident, not during it.

Part B: Which Applications Depend on Active Directory, and Which Dependencies Run the Other Way

What applications need from Active Directory

Most people picture applications as separate from the directory. In practice, hundreds of them lean on it. File servers use directory identifiers to enforce access. Databases that use Windows authentication stop when Kerberos stops. Failover clusters and availability groups rely on computer objects in the directory. Messaging, collaboration and virtual desktops authenticate staff against it. Enterprise applications bind to it over LDAP, use Kerberos keytabs or accept sign-in assertions from federation. VPN, wireless, RADIUS and multifactor servers use it to let people in at all. Even non-Windows servers, appliances and storage arrays often use directory groups. Each of these has service accounts and service principal names, and these are the most common reason an application fails to start after a recovery: nobody knows who owns the account or where its password is stored.

What Active Directory needs from everything else

The dependency also runs the other way. Domain controllers need a network with the right ports open, DNS to find each other, accurate time because Kerberos fails when clocks drift more than five minutes, and storage and a hypervisor to run on. They often depend on certificates for secure traffic, on backup platforms for recovery and on monitoring and privileged access tools for administration.

The loops that deadlock a recovery

The danger is the circular dependency. The hypervisor management console authenticates against the directory that runs on the hypervisor. The backup server is domain-joined and cannot start the restore of the domain controller it needs. The password vault that holds break-glass credentials runs on a server that needs the directory to start. DNS is stored in the directory, and the directory needs DNS to find replication partners. The certificate authority needs the directory, and the domain controllers need certificates from the authority. The tools the service desk uses to reset passwords authenticate with the directory. Any one of these can stall an otherwise good plan.

What to do about it

  • Draw the map in both directions and name the loops. Test the cold start of the whole estate, not only the directory.
  • Give the hypervisor, backup, vault and monitoring local or separately managed authentication, and keep sealed break-glass credentials outside the directory.
  • Keep an immutable, offline copy of directory system state, and time a restore at scale.
  • Inventory service accounts, assign owners, move to managed service accounts where possible and remove them from privileged groups.
  • Reduce the paths to tier zero: replication rights, unconstrained delegation, legacy authentication, web enrollment and broad Group Policy delegation.
  • Write the Sr. Leadership decision brief now, and rehearse it with a different attack path every time.
