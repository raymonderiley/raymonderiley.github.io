Immutable vs. Air-Gapped Backups: Understanding the Difference—and Why Resilience May Require Both

Backups are often described as an organization's last line of defense against ransomware, accidental deletion, system failure, and major outages. But having a backup is not the same as having a backup that an attacker cannot destroy—or a copy that remains available when the production environment is compromised. Two important protection strategies address these risks: immutability and air-gapping.

The terms are sometimes used interchangeably, but they describe different safeguards. Understanding what each one does, where each can fall short, and when to combine them is essential to building a recovery strategy that works under pressure. This article covers the concepts first, then walks through how Amazon Web Services (AWS), Microsoft Azure, and Google Cloud Platform (GCP) implement each control—and where the gaps tend to hide.

What Is an Immutable Backup?

An immutable backup is a protected copy of data that cannot be changed or deleted for a defined retention period. The protection is commonly enforced through a storage-level control, such as write-once-read-many (WORM) retention, an object-lock policy, or a supported immutable repository. Once the protected data is committed, ordinary administrative actions should not be able to alter or remove it before the retention period expires.

Consider a backup retained as immutable for 30 days. If ransomware compromises a production server—or an attacker obtains powerful administrative credentials—the attacker should not be able to erase or rewrite that protected recovery point during its locked period. The organization has a preserved version to investigate and, if validated as clean, restore.

Not all immutability is equal. Many platforms offer two flavors: a governance-style lock that privileged users with a specific permission can still override, and a compliance-style lock that no one—including the account's root or highest-privileged identity, and in some cases the provider's own support staff—can shorten or remove once it is committed. Governance-style locks are useful for testing and for protecting against accidents. Compliance-style locks are what actually stand up to a fully compromised administrator.

The key idea: Immutability protects the integrity and retention of a backup copy. It does not necessarily make that copy unreachable from the production network.

What Is an Air-Gapped Backup?

An air-gapped backup is separated from the systems it protects so that a compromise of the production environment cannot readily reach the backup copy. The traditional example is removable media—such as tape—that is disconnected from the network and stored securely after the backup is written.

Air-gapping can also be implemented through carefully designed logical isolation. A secondary environment may have separate network paths, independent administrative credentials, restricted connectivity, and tightly controlled windows when data can be transferred. The important question is not simply whether the backup sits in another location. It is whether a compromised production account or system can access, modify, or destroy it.

Physical disconnection generally provides a stronger form of separation than a network-isolated system that remains online. Logical isolation can still be valuable, but it must be designed and tested carefully. A backup that is described as “isolated” but can be reached through shared credentials, management systems, or open network paths may not provide the protection decision-makers expect.

Immutable vs. Air-Gapped: How Are They Different?

The simplest distinction is this: immutability is about preventing changes or deletion during a retention period; air-gapping is about limiting connectivity and access. One protects the backup from being altered. The other helps keep an attacker from reaching it in the first place.

  • Immutable only: A backup can be protected against deletion or modification while remaining online and reachable by authorized systems. This is valuable, but an attacker may still disrupt backup services, compromise management infrastructure, or target other connected resources.
  • Air-gapped only: A disconnected copy is difficult for a network-based attacker to reach. However, if the copy is not protected against tampering before it is disconnected—or if it is reconnected and exposed—it may still be vulnerable to corruption, mishandling, or malicious changes.
  • Both together: An immutable copy that is also isolated combines protection against unauthorized alteration with reduced network exposure. This layered approach can provide stronger resilience than relying on either control alone.

How These Strategies Work On-Premises

In an on-premises data center, an organization may send backups from production servers or virtual machines to a dedicated backup repository. One option is a hardened repository configured to enforce immutability for a specified number of days. Administrative access should be tightly restricted, credentials should be separate from the production identity environment where practical, and changes to retention or backup configuration should be monitored.

A second copy can then be sent to a separate location or medium. That might be offline tape, an isolated storage system, or another repository in a separately administered environment. To qualify as a meaningful air gap, the secondary copy must not remain freely accessible through the same production network and credentials that an attacker could compromise.

These copies address different failure scenarios. The immutable repository can provide relatively accessible recovery points after a ransomware incident. The isolated copy provides another option if the primary site, backup management environment, or connected repository is compromised or unavailable. Neither copy eliminates the need to verify that the data is clean and usable before restoring it.

What About Cloud Backups?

Cloud storage can provide durable off-site backup capacity and storage-level retention controls. Major cloud platforms offer mechanisms for protecting stored objects from deletion or modification for a defined period. Organizations can strengthen separation by using distinct accounts, subscriptions, or projects; independent privileged identities; narrowly scoped permissions; and restricted network access.

However, storing a backup in the cloud does not automatically make it air-gapped. If compromised production credentials or a connected management plane can still reach and delete the copy, the separation may be weaker than intended. Cloud immutability and isolation should therefore be treated as deliberate architecture and identity decisions—not simply as a checkbox or a geographic location.

In the cloud, there is no cable to unplug. A true physical air gap is not something a hyperscaler offers for your data. What the providers offer instead is a logical air gap: backups held in a separate security boundary—often an account, tenant, or project the provider manages—reachable only through the backup service's own APIs and governed by identities and approvals that live outside the production blast radius. The three major providers have each converged on that model, but they implement it differently.

A note on currency: Cloud backup features evolve quickly—new regions, new supported workloads, and new approval controls appear regularly. The descriptions below reflect each provider's capabilities as of late 2026. Always validate feature availability, supported resource types, and regional coverage against the provider's current documentation before designing around them.

AWS: Vault Lock, Object Lock, and Logically Air-Gapped Vaults

Amazon Web Services

AWS provides immutability at two layers—the storage layer (Amazon S3) and the backup service layer (AWS Backup)—and has built a dedicated logically air-gapped vault on top of the backup layer.

Immutability: S3 Object Lock

Amazon S3 Object Lock applies WORM protection to individual object versions in a versioned bucket. It supports two retention modes:

  • Governance mode: Most users cannot overwrite or delete a locked object version, but identities granted a special bypass permission can. Useful for testing retention settings or guarding against accidental deletion.
  • Compliance mode: No user—including the account root user—can delete the protected version or shorten its retention period until it expires. This is the mode that resists a compromised administrator.
  • Legal hold: An independent flag that prevents deletion indefinitely until it is explicitly removed, regardless of retention dates. Useful for investigations and litigation.

S3 Object Lock is the foundation many third-party backup products use when they write to S3 as an immutable target. If your backup software lands data in S3, confirm that the bucket was created with Object Lock enabled, which mode is applied, and that the retention period aligns with your recovery objectives.

Immutability: AWS Backup Vault Lock

AWS Backup stores recovery points in backup vaults. AWS Backup Vault Lock enforces WORM protection on those vaults, again in governance or compliance mode. In compliance mode, a lock configuration includes a grace period (sometimes called a cooling-off period) during which the lock can still be tested and removed. Once that period expires, the lock becomes immutable: no one can delete the vault's recovery points early, change the minimum or maximum retention, or remove the lock itself.

That permanence is the point—and also the risk. A compliance-mode lock with an overly long retention period commits the organization to paying for that storage. Retention settings should be agreed with finance, legal, and records management before the grace period ends.

Air-Gapping: Logically Air-Gapped Vaults

AWS Backup also offers a logically air-gapped vault, a separate vault type designed for cyber recovery. According to AWS documentation, each logically air-gapped vault comes equipped with a vault lock in compliance mode, so immutability is built in rather than optional. Backups in these vaults are encrypted and isolated from the account's own key management, which reduces the risk that an attacker can destroy recoverability by deleting or disabling encryption keys.

The vault can be shared with other accounts for recovery through AWS Resource Access Manager (RAM). That means a separate recovery account can restore directly from the vault without first copying data back into a potentially compromised production account. AWS has steadily expanded the model: backups can now be written directly to logically air-gapped vaults, copied across accounts and Regions, and shared for recovery, and AWS added six more Regions to the feature in July 2026.

Recovery Governance: Multi-Party Approval

The hardest scenario is not a deleted backup—it is losing access to the account that owns the backups. To address this, AWS integrated logically air-gapped vaults with Multi-party approval from AWS Organizations. Organizations create approval teams of highly trusted individuals and associate them with the vault; if the owning account becomes inaccessible due to a malicious or accidental event, those approvers can collectively authorize a separate recovery account to access the backups. AWS recommends operating this with two or more separate AWS Organizations, so the recovery path does not depend on the same organization an attacker may have compromised. As of May 2026, approvers must also complete one-time password (OTP) verification when voting on these approvals, applied automatically at no extra charge.

Practical AWS Design Pattern

  • Back up workloads into a standard vault in the workload account with Vault Lock applied for fast, routine restores.
  • Copy (or back up directly) to a logically air-gapped vault in a dedicated, tightly controlled backup account.
  • Share that vault through RAM with an isolated recovery account—and, ideally, a forensic account for investigating suspect recovery points.
  • Configure Multi-party approval with approvers whose identities are not managed by the production organization.
  • Apply service control policies (SCPs) that deny backup deletion and vault-policy changes, and alert on any attempt.
  • Use AWS Backup restore testing to schedule automated restores and validate recovery time.

Azure: Immutable Vaults, Soft Delete, and Resource Guard

Microsoft Azure

Azure's approach layers several controls on its backup vaults—immutability, soft delete, and a separate authorization gate for destructive operations—on top of storing vaulted backup data outside the customer's own subscription.

Isolation by Design: Vaulted Backups

Azure Backup uses two vault types: Recovery Services vaults (for workloads such as Azure VMs, SQL Server and SAP HANA in VMs, and Azure Files) and Backup vaults (for newer workloads such as Azure Disks, Azure Blobs, and Azure Database for PostgreSQL). Microsoft states that vaulted backup data is stored in a Microsoft-managed Azure subscription and tenant. That separation is Azure's form of logical air-gapping: a customer administrator cannot browse, encrypt, or delete the underlying storage directly, and can act on it only through the backup service.

Be aware that some Azure workloads offer operational (snapshot) tiers that live inside the customer's own subscription alongside the protected resource. Those are excellent for quick restores, but they do not carry the same isolation as the vault tier. Cyber recovery designs should ensure critical workloads are protected in the vault tier.

Immutability: Immutable Vaults

Azure Backup's immutable vault setting blocks operations that could lead to the loss of recovery points, such as deleting recovery points before they expire or reducing retention in backup policies. The setting has three states:

  • Disabled: No immutability protection.
  • Enabled: Protection is applied but can still be turned off—suitable for validating that operations work as expected.
  • Enabled and locked: Protection becomes irreversible. Immutability can no longer be disabled on the vault.

Recoverability: Enhanced Soft Delete

Soft delete retains deleted backup data for an additional period so it can be recovered. Azure's enhanced soft delete allows the retention window to be extended and can be made always-on, meaning an administrator—or an attacker with administrative credentials—cannot simply disable soft delete before deleting backups. Soft delete is not immutability on its own, but it closes a common attack pattern: turning off protections, then purging data.

Separation of Duties: Multi-User Authorization with Resource Guard

The most important Azure control for resisting a compromised administrator is Multi-user authorization (MUA). Azure Backup uses a separate Azure resource called Resource Guard as an additional authorization layer for critical operations on both Recovery Services vaults and Backup vaults. For it to work as intended, Microsoft notes that the Resource Guard must be owned by a different user, and the vault administrator must not hold Contributor, Backup MUA Admin, or Backup MUA Operator permissions on it.

In practice, a security team owns the Resource Guard—ideally in a different subscription or even a different Microsoft Entra tenant, which Azure supports. When a backup admin wants to perform a protected operation such as disabling soft delete, reducing retention, or stopping protection and deleting data, they must request just-in-time access on the Resource Guard. A stolen backup-admin credential alone is no longer enough to destroy the backup estate.

Storage-Layer Immutability: Azure Blob Immutable Storage

For organizations that write backups to Azure Blob Storage with third-party backup software, Azure offers immutable storage for blobs. Time-based retention policies and legal holds can be applied at the container or individual blob-version level. A time-based retention policy can be left unlocked for testing or locked to make it compliant—after which the retention interval can be extended but not shortened, and the policy cannot be deleted.

Practical Azure Design Pattern

  • Protect critical workloads in the vault tier, not only the operational (snapshot) tier.
  • Enable enhanced soft delete in always-on mode, then enable and lock vault immutability once retention has been validated.
  • Place the Resource Guard in a separate subscription or tenant owned by the security team, and require just-in-time approval for critical operations.
  • Use cross-region restore or geo-redundant vault storage for regional resilience.
  • Monitor the vault's security posture with Azure Backup's security settings and alert on attempts to change protection.
  • Restrict who can modify Azure Policy and role assignments on backup subscriptions—these are just as critical as the vaults themselves.

Google Cloud: Backup Vaults, Bucket Lock, and Project Isolation

Google Cloud Platform

Google Cloud combines a managed, isolated backup vault in its Backup and DR Service with retention controls in Cloud Storage for organizations using their own backup tooling.

Immutability and Air-Gapping: Backup and DR Service Backup Vaults

The Google Cloud Backup and DR Service offers backup vaults described as immutable (contents cannot be modified once created) and indelible (backups cannot be deleted before their enforced retention expires). Google describes the backup vault as a Google-managed regional resource that isolates backups through enforced retention periods and project-level identity isolation.

Backups stored in a vault live in Google-managed projects and are logically air-gapped from the customer's own Google Cloud project. Access to vault data is provided only through the Backup and DR Service's APIs and console—not through direct storage access. This mirrors the Azure and AWS approach: the customer controls policy and restores, but the underlying storage sits outside the customer's direct reach.

Minimum Enforced Retention

Each backup vault supports a minimum enforced retention period, configurable up to 99 years. During that window, backups cannot be deleted or altered—even by project owners. As with AWS compliance-mode locks, this is powerful and permanent, so the retention value needs business agreement before it is set. Backup vaults can store data in regional or compatible multi-regional locations, which adds geographic resilience to the logical separation.

Storage-Layer Immutability: Cloud Storage Retention Controls

For organizations that write backups to Cloud Storage buckets using third-party backup software, Google Cloud provides several controls:

  • Bucket Lock: A bucket-level retention policy that prevents objects from being deleted or overwritten until they reach a specified age. Once the policy is locked, it cannot be removed or shortened—only extended.
  • Object Retention Lock: Retention configured on individual objects, with an unlocked mode (adjustable) and a locked mode (cannot be reduced or removed).
  • Object holds: Event-based and temporary holds that prevent deletion until the hold is released, useful for investigations.
  • Soft delete: Deleted objects are retained for a configurable window so they can be restored—helpful against accidental or malicious deletion, though not a substitute for a locked retention policy.

Isolation Through the Resource Hierarchy

Google Cloud's resource hierarchy—organization, folders, and projects—supports deliberate separation. Placing backup infrastructure in a dedicated folder and project, with its own IAM bindings, organization policy constraints, and VPC Service Controls perimeter, reduces the chance that a compromised workload project or identity can reach backup resources. As with any cloud, the weakest link is often a highly privileged identity at the organization level that can reach every project.

Practical GCP Design Pattern

  • Use Backup and DR Service backup vaults with a minimum enforced retention period for critical Compute Engine, disk, and database workloads.
  • Choose multi-region vault locations where supported to protect against regional outages.
  • For third-party backup targets in Cloud Storage, apply and lock a retention policy rather than relying on soft delete alone.
  • Isolate backup administration in a dedicated project and folder, enforce VPC Service Controls, and limit organization-level roles.
  • Audit Cloud Audit Logs for changes to backup plans, vaults, and retention policies, and alert on them.

Comparing the Three Clouds

Although the product names differ, the three providers have arrived at a remarkably similar architecture. Mapping their capabilities to the two core controls makes them easier to compare.

Immutability

  • AWS: S3 Object Lock (governance or compliance mode, plus legal hold) and AWS Backup Vault Lock (governance or compliance mode with a grace period before the lock becomes permanent).
  • Azure: Immutable vaults (enabled, or enabled and locked), enhanced always-on soft delete, and Blob immutable storage with time-based retention and legal holds.
  • GCP: Backup vault minimum enforced retention (immutable and indelible), Cloud Storage Bucket Lock, Object Retention Lock, object holds, and soft delete.

Logical Air-Gapping

  • AWS: Logically air-gapped vaults with built-in compliance-mode lock, service-owned encryption, sharing to recovery accounts via RAM, and cross-account and cross-Region copy.
  • Azure: Vaulted backup data held in a Microsoft-managed subscription and tenant, accessible only through Azure Backup.
  • GCP: Backup vaults held in Google-managed projects, accessible only through Backup and DR Service APIs and console.

Protection Against a Compromised Administrator

  • AWS: Compliance-mode locks plus Multi-party approval with OTP verification, ideally anchored in a separate AWS Organization.
  • Azure: Multi-user authorization through a Resource Guard owned by a different team, optionally in a different tenant.
  • GCP: Enforced retention that project owners cannot override, combined with careful separation of organization- and project-level IAM.
The pattern across all three: immutability is enforced by the provider, the backup storage lives in a provider-managed boundary outside the customer's direct reach, and destructive or recovery-critical actions require identities that sit outside the production blast radius. The customer's job is to configure those controls correctly—and to make sure their own identity design does not quietly undo them.

Common Pitfalls in Cloud Backup Protection

The native controls are strong, but recovery failures usually come from how they are configured and operated. These are the gaps that appear most often in real assessments and exercises.

  • Governance mode mistaken for compliance mode: A lock that a privileged identity can bypass protects against accidents, not against an attacker holding that privilege.
  • Snapshots treated as backups: Operational snapshots stored in the same account, subscription, or project as the workload share its blast radius.
  • One identity plane for everything: If the same identity provider, break-glass account, or organization administrator can reach both production and backup environments, the logical air gap may be thinner than it looks.
  • Encryption keys in the blast radius: Backups encrypted with customer-managed keys can be rendered unrecoverable if an attacker deletes or disables those keys. Protect key deletion with the same rigor as backup deletion.
  • Retention set without business agreement: A permanent lock with the wrong retention period becomes either a cost problem (too long) or a recovery problem (too short to cover attacker dwell time).
  • Coverage gaps: Not every resource type is supported by every vault type or Region. SaaS data, configuration state, and infrastructure-as-code repositories are often left out entirely.
  • No clean recovery environment: Restoring into the same compromised account or network can reinfect recovered systems. Plan an isolated recovery landing zone in advance.
  • Untested approval workflows: Multi-party approval and Resource Guard requests only help if approvers know their role, can be reached during an incident, and have practiced the process.

Choosing One, or Building a Layered Strategy

An organization may begin with immutability when its immediate priority is ensuring that backup copies cannot be deleted during a defined retention period. It may prioritize air-gapping when reducing network exposure is the central concern, or when it needs an offline recovery copy. In practice, many organizations benefit from combining the two: maintain immutable backups for accessible recovery, and preserve an additional isolated or offline copy for scenarios in which connected systems are no longer trustworthy.

The right design depends on recovery objectives, data volume, network capacity, retention requirements, operational staffing, and the cost of maintaining separate infrastructure. It also depends on how quickly the organization must restore critical services. A protected copy is only one part of disaster recovery; compute capacity, networking, identity services, application dependencies, and a tested recovery sequence matter just as much.

For organizations running across multiple clouds—or a mix of cloud and on-premises—consider whether a copy of the most critical data should also live outside the primary provider entirely. Provider-native logical air gaps protect well against account- and tenant-level compromise, but a separately administered copy with a different provider, a dedicated cyber-recovery vault, or offline media protects against a broader set of scenarios, including loss of access to the provider relationship itself.

Protection Is Only Proven When Recovery Works

A backup strategy should be measured by more than successful backup jobs. Organizations should regularly test whether protected copies can be accessed by authorized recovery teams, whether retention controls resist unauthorized deletion, and whether isolated copies are genuinely separated from production. Recovery exercises should include the systems that support the recovery process itself, such as identity, DNS, network services, and backup management.

Testing should also reflect business priorities. Critical infrastructure may need to return before databases and application services can operate. Large databases may require additional time for restoration, log processing, consistency checks, and application validation. Measuring these steps in realistic exercises helps determine whether recovery time objectives are achievable—and exposes gaps before a real incident.

In the cloud, a few tests are especially revealing:

  1. Attempt to delete a locked recovery point using the most privileged production identity, and confirm the platform refuses.
  2. Simulate loss of the backup-owning account, subscription, or project, and restore from the isolated vault into a separate recovery environment.
  3. Run the full approval workflow—Multi-party approval on AWS or a Resource Guard request on Azure—with the real approvers, on a clock.
  4. Validate that encryption keys required for restore are available from the recovery environment.
  5. Measure end-to-end time from declaring an incident to a validated, running application—not just the time to complete a restore job.
Bottom line: Immutable and air-gapped backups are not competing ideas. They solve different parts of the same resilience problem. Immutability helps preserve a trustworthy recovery point; air-gapping helps keep that recovery point out of an attacker's reach. AWS, Azure, and Google Cloud all provide strong native building blocks for both—but none of them configures your identity boundaries, retention decisions, or recovery runbooks for you. A well-designed strategy uses the controls that match the organization's risks—and proves the result through regular recovery testing.
