Active Directory Recovery Playbook Template

Active Directory Compromise & Recovery (Template)

Purpose and How to Use This Template

This is a fill-in template for a company's Active Directory recovery playbook. It is written to be completed from the results of the tabletop exercises in this series and kept up to date after each one. It follows the real order of an Active Directory recovery, from the decision to declare through to hardening, and it records who decides, who acts, how long each step takes and how it is verified.

Store the completed playbook where it can be read when the directory is down: offline copies, a printed copy in a sealed location and a copy in a store that does not authenticate with the directory. Test it at least once a year, and again after any major change to the directory, the hypervisor, the backup platform, PKI or hybrid identity.

Activation criteria

  • ☐ More than one domain controller encrypted or unreachable without a known cause
  • ☐ Unexplained change to Domain Admins, Enterprise Admins, Schema Admins or protected accounts
  • ☐ Evidence of replication of secrets from a host that is not a domain controller
  • ☐ Evidence of forged tickets or abnormal ticket lifetimes
  • ☐ Loss of all domain controllers in any domain
  • ☐ Compromise of the certificate authority, federation or synchronization servers
  • ☐ Compromise of the hypervisor management plane or backup platform
  • ☐ Notification from law enforcement, a vendor or a regulator that directory credentials are exposed

6. Choosing the Recovery Path

Describe in advance what evidence would lead to each path, so the decision is fast and defensible in the moment.

Path A: In-place eviction

Suitable only when evidence shows a narrow compromise, no replication of secrets, no persistence in the directory and no compromise of PKI, hypervisor or federation.

Your criteria and conditions

Path B: Forest recovery from a clean backup

Suitable when a verified clean system state backup exists and the cost of lost changes is acceptable.

Your criteria, the oldest acceptable backup and the lost-change tolerance

Path C: Rebuild into a new forest

Suitable when no clean backup exists, when persistence is likely to survive a restore or when a state-level adversary is suspected.

7. Recovery Runbook

Each step has fields for owner, estimated duration and verification. Fill in the estimates from tested restores, not from guesses. Add your own steps where your environment differs.

1. Confirm the failure and isolate

Establish that no healthy domain controller exists in at least one domain, or that the directory cannot be trusted. If a healthy writable domain controller remains in each domain, the better path is usually to seize roles and promote new domain controllers rather than perform a full forest recovery. Disconnect the remaining domain controllers from the network so they cannot replicate unwanted data back into the restored directory.

2. Document the forest

Record every domain, domain controller, FSMO holder, site, trust, global catalog, DNS zone and functional level. Identify which domain controller in each domain has the best recent backup and is writable. Use a read-only domain controller as a source only as a last resort; it does not hold secrets in the same way.

3. Choose backups younger than the tombstone lifetime

Backups older than the tombstone lifetime, which is 180 days in current forests by default, can reintroduce deleted objects and cause lingering object problems. Choose the newest backup that meets the proof of cleanliness required by the scenario.

4. Restore one writable domain controller per domain, root domain first

Restore the system state offline into an isolated network, non-authoritatively, in directory services restore mode. Start with the forest root domain, then each child domain. Do not restore other domain controllers from backup.

14. Validation Before Reconnecting

  • ☐ Replication is healthy between all restored and rebuilt domain controllers
  • ☐ SYSVOL is present and consistent
  • ☐ DNS zones and service records are correct and clients can find domain controllers
  • ☐ Time source and hierarchy are correct
  • ☐ Kerberos and LDAP tests pass from each site
  • ☐ Privileged group membership matches the approved baseline
  • ☐ Directory permissions and delegation match the approved baseline
  • ☐ Group Policy objects match the approved baseline and were reviewed
  • ☐ Protected account template matches the baseline
  • ☐ No unexpected key attributes, identity history or delegation settings
  • ☐ Domain controllers and management servers are fully patched and enforcing
  • ☐ Identity threat detection is active and monitored
  • ☐ The compromise assessment found no remaining attacker activity
  • ☐ Sr. Leadership has accepted the residual risk in writing

16. Reference Commands for Facilitators and Engineers

These are examples to help you plan. Confirm each against current vendor guidance, test it in a lab and adapt it to your environment before use. Never run them on a production directory without a tested procedure and change approval.

# Replication and health
repadmin /replsummary
repadmin /showrepl *
repadmin /syncall /AdeP
dcdiag /v /c /e
dcdiag /test:dns /v

# Operations masters
netdom query fsmo
ntdsutil
  roles
  connections
  connect to server <restored-dc>
  quit
  seize schema master
  seize naming master
  seize PDC
  seize RID master
  seize infrastructure master

# Time on the PDC emulator
w32tm /config /manualpeerlist:"<reliable-source>" /syncfromflags:manual /reliable:yes /update
w32tm /resync

# Secure channel and computer account problems
nltest /sc_verify:<domain>
Test-ComputerSecureChannel -Repair
Reset-ComputerMachinePassword

# Install from media for additional domain controllers
ntdsutil
  activate instance ntds
  ifm
  create sysvol full <path>

# Privileged group review
Get-ADGroupMember "Domain Admins" -Recursive
  • For metadata cleanup after seizing roles, remove the objects of domain controllers that were not restored, using the directory management tools or the metadata cleanup function in ntdsutil.
  • For the RID pool, raise the available pool value on the RID Manager object by 100,000 and invalidate the current pool using the documented directory operation, as described in Microsoft's forest recovery guidance.
  • For krbtgt, use a documented and tested script or procedure, run it twice per domain, and wait between resets for replication and for the maximum ticket lifetime.
  • For trusts, reset the trust password on both sides of each trust using the directory tools.
