Active Directory Recovery Tabletop Exercise Template

Active Directory Compromise & Recovery (Template)

How to Use This Template

This is a fill-in worksheet for facilitating a tabletop exercise on recovering Active Directory after a compromise. It is specific to directory recovery: it captures the forest facts, the backup proof, the credential reset order, the dependency loops and the recovery milestones that determine whether a real recovery would succeed. Complete sections 1 to 6 before the exercise, sections 7 to 11 during it and sections 12 to 15 afterward. Print it, copy it into your own document, or keep one copy per run.

Pair it with the flagship exercise or with any of the twenty attack-path scenarios, and with the playbook template, which is the document you update from the results. Do not enter real credentials, real hostnames of sensitive systems or personal data into this worksheet.

Objectives for this run

Tick the objectives you will test and write the measure of success next to each.

  • ☐ Declare and communicate. Participants declare an Active Directory compromise on partial evidence, name who has authority to declare it and state in plain language what is known, assumed and unknown.
  • ☐ Establish an out-of-band operating mode. The group names the channels, accounts and tools it will use when the directory is untrusted, including break-glass access to hypervisors, backup and network devices.
  • ☐ Scope under uncertainty. The group states what it will assume about credentials, backups, PKI, federation and the hypervisor, and what evidence would change those assumptions.
  • ☐ Choose a recovery path. The group compares in-place eviction, forest recovery from a clean backup and rebuild into a new forest, and records the criteria for each, including the point at which it would escalate to Sr. Leadership.
  • ☐ Prove a clean restore point. The group describes how it would find, verify and scan candidate backups in isolation, and what it would do if the oldest available backup is still compromised.
  • ☐ Sequence the technical recovery. The group orders the restoration of the first domain controller, FSMO role seizure, metadata cleanup, DNS, time, credential resets, additional domain controllers and global catalogs, with the reason for each step.
  • ☐ Reset credentials in the right order. The group sequences the reset of krbtgt, trust, privileged, service, domain controller computer account and DSRM passwords, and names what will break at each step.
  • ☐ Protect the recovery from reinfection. The group names the controls it will apply before reconnecting: isolation, tiered administration, clean administrative hosts, identity threat detection and patching of domain controllers and management servers.
  • ☐ Return applications and users in tiers. The group agrees an order for identity-dependent platforms and applications, who accepts each tier as ready and how users will be reset at scale without handing the attacker a social engineering path.
  • ☐ Support decisions by Sr. Leadership. The group prepares options, costs, times and risks that a Sr. Leader or board of directors can decide on, and records each decision in the playbook.

  • ☐ Path 15: A Forged-Ticket Backdoor From an Earlier Undetected Breach Survives Every Cleanup and Returns With Ransomware (Credential Theft)
  • ☐ Path 16: Write Access to an Account Attribute Lets an Attacker Add a Key and Authenticate as a Privileged Account (Excessive Privileges)
  • ☐ Path 17: A Chain of Inherited Permissions Leads From a Help Desk Account to Domain Admin and a Hidden Backdoor in the Protected Accounts Template (Excessive Privileges)

  • ☐ Path 19: A Poorly Secured Acquired Domain Becomes the Entry Point Into the Forest Through a Trust and Forged SID History (Weak Connected Infrastructure)
  • ☐ Path 20: Legacy Mail Server Permissions on the Domain Object Let an Attacker Grant Themselves Replication Rights (Weak Connected Infrastructure)

  • ☐ Disaster variant (no attacker)

4. Readiness Checklist Before the Exercise

  • ☐ A current inventory of forests, domains, domain controllers and FSMO holders exists outside the directory
  • ☐ At least one recent system state backup per domain is known, with its date and location
  • ☐ An immutable or offline copy of directory backups exists and the owner is named
  • ☐ Break-glass credentials for hypervisors, storage and network are sealed and their holders are named
  • ☐ The recovery inventory and playbook can be opened without the directory
  • ☐ An out-of-band communication channel is agreed and tested
  • ☐ A clean administrative workstation or build process exists
  • ☐ The service desk has an agreed reset verification script
  • ☐ Counsel, communications and Sr. Leadership have agreed to attend
  • ☐ Participants have read the ground rules

5. Ground Rules to Confirm

  • This is a no-fault exercise. The aim is to find gaps in plans, authority and tooling, not to assign blame to people or teams.
  • Treat all information in the scenario as true unless a facilitator corrects it. Do not fight the scenario by assuming a control worked unless it is documented.
  • Assume the domain directory cannot be trusted. Do not assume you can use domain accounts, domain-joined tools or domain-based messaging unless the group has agreed how.
  • Ask each role for an individual answer first, then open the discussion. Where the room is quiet, ask the next person whether they agree and why.
  • Use real names for roles and real systems from your own environment where you can, but do not use real credentials, real hostnames of sensitive systems or live data.
  • Do not run tools or commands on live systems during the exercise. Describe what you would do and what you would expect to see.
  • Record decisions, assumptions and open questions in the decision log as the exercise runs.
  • Facilitators may pause to correct a technical error but should prefer asking a question over giving the answer.

8. Decision Log

The scribe records each decision as it is made. Use one entry per decision. The eight standing decisions below should each appear at least once.

  • Declare: Who may declare? What evidence is enough? What do we assume once declared?
  • Isolate: Which segments, sites and management tiers are cut off, and what is the business effect?
  • Choose path: In-place eviction, forest recovery or rebuild?
  • Select restore point: Which backup, from what date, with what proof?
  • Restore: Which domain controller is restored first and where?
  • Reset: In what order and with what interval do we reset secrets?
  • Reconnect: Which sites and tiers return first, and who accepts them?
  • Harden: What do we change now and what waits?

13. Dependency Loop Test Results

For each loop, record whether the group recognized it, whether the plan has a break, and who owns the break.

  • ☐ The directory runs on a hypervisor whose management accounts are in the directory.
  • ☐ The backup server is domain-joined and needs the directory to authenticate the restore.
  • ☐ The certificate authority needs the directory, and domain controllers need certificates from the authority.
  • ☐ The password vault holds break-glass credentials but runs on a server that needs the directory to start.
  • ☐ DNS is stored in the directory, and the directory needs DNS to find replication partners.
  • ☐ Monitoring and logging servers need the directory to log on, and are the only way to see attacker activity.
  • ☐ The service desk tools used to reset passwords authenticate with the directory.
