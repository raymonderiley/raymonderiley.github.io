Cross-Cloud Terraform State File Corruption and Resource Orphan

Hybrid Cloud (AWS & Azure)

Exercise Overview

This tabletop exercise examines a corrupted Terraform state file that manages resources in both AWS and Azure, so plans show mass destruction and recreation, orphaned resources continue to run and cost money, and a careless apply would delete production components.

Participants are working-level: infrastructure engineers, cloud platform engineers, application owners, the service desk, cloud operations and monitoring staff, the AWS and Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of state backends, locking, versioning, import and state surgery, drift detection and change freeze.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Mulberry Logistics manages most infrastructure in one Terraform workspace with a remote state in an S3 bucket with a DynamoDB lock. About 3,000 resources across AWS and Azure are in the state. Bucket versioning is enabled but nobody has tested restoring state.

At 14:00 on Thursday, two pipelines run concurrently after a lock timeout misconfiguration. A partial write corrupts the state file. The next plan shows 1,100 resources to destroy and recreate, including databases and load balancers. A pipeline on auto-approve for a minor change runs and begins destroying resources before a cancel lands. Some resources are destroyed, others are no longer tracked and keep running.

What the team does not yet know: which resources were destroyed versus orphaned, whether the previous state version is consistent with reality, auto-approve is still enabled on other pipelines, and a destroyed database had a recent backup of uncertain age.

Exercise Objectives

  • Recognize state corruption. Participants read plan output and state history to confirm corruption.
  • Freeze changes. The team stops pipelines and prevents further applies.
  • Assess real versus recorded state. Engineers inventory actual resources versus state.
  • Restore state safely. Participants choose between version restore and import.
  • Recover destroyed resources. The team recovers destroyed components from backups and code.
  • Improve IaC safety. Participants review locking, approvals and state backups.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Freeze all pipelines that can apply to this workspace before any investigation, and record the freeze time.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Mass destroy plans and destroyed resources lead to declaration.

T+00:30 — Containment. Pipelines are frozen and damage assessed.

T+01:15 — Diagnosis. State and reality are compared.

T+02:00 — Remediation planning. A restore and recovery plan is agreed.

T+03:00 — Execution. State and resources are repaired in order.

T+04:30 — Stabilization. Services stabilize.

T+06:00 — Validation. State matches reality.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: A corrupted state turns a small change into a mass destroy

Time frame T+00:00 · Variant Primary

Situation

It is 14:30. A pipeline destroyed resources and a plan shows 1,100 more to destroy. Some resources are gone and others run untracked.

The infrastructure engineer finds two concurrent runs corrupted the state after a lock timeout misconfiguration.

Auto-approve remains on other pipelines. A destroyed database has a backup of uncertain age.

Facilitator provides: state versions, plan output, pipeline logs and the resource inventory.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize freezing all pipelines.
  • Set the next update at T+00:20.
Infrastructure Engineering (IaC)
  • Freeze pipelines.
  • Review state.
  • Plan restore.
Cloud Platform Engineering (AWS & Azure)
  • Inventory.
  • Find orphans.
  • Recreate carefully.
Application Owners & Service Desk
  • Rank components.
  • Service desk: issue the holding message.
  • Verify services.
Cloud Operations & Monitoring
  • Watch outages.
  • Build comparison.
  • Preserve logs.
AWS, Microsoft & Carrier Support Liaison
  • Open cases.
  • Ask about soft delete.
  • Record guidance.
Business Continuity & Communications
  • Inform leadership.
  • Prepare the first update.
  • Plan customer notice.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about change control duties.
  • Start the evidence log.

Discussion questions

  1. What do you freeze first?
  2. How do you know what was destroyed and what is orphaned?
  3. Do you restore a previous state version and how do you test it?
  4. How do you recover the destroyed database?
  5. What do you do about orphan cost and exposure?
  6. Who approves any apply?
  7. What do customers hear?
  8. Why did auto-approve exist for production?

Facilitator notes

  • Do not reveal other auto-approve pipelines until T1 audits pipelines.
  • If players apply to repair, stop and discuss.
  • Look for freeze first.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes accurate infrastructure state and safe change and sets approval rules for risky changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes emergency changes, exceptions and spend.
  • Decides on stakeholder communications and the end of the incident.

Infrastructure Engineering (IaC)

  • Disables pipelines and locks the workspace.
  • Reviews state versions and the corruption event.
  • Plans state restore or rebuild by import.
  • Plans plan review before any apply.
  • Records actions and results for the scribe.

Cloud Platform Engineering (AWS & Azure)

  • Inventories actual resources in AWS and Azure.
  • Identifies orphans and destroyed items.
  • Recreates critical components carefully.
  • Tracks cost of orphans.
  • Records actions and results for the scribe.

Application Owners & Service Desk

  • Application owners rank destroyed components.
  • The service desk logs impact.
  • Owners verify recovered services.
  • Prepare validation checks.
  • Records actions and results for the scribe.

Cloud Operations & Monitoring

  • Watches for related outages and cost spikes.
  • Builds a resource comparison view.
  • Preserves logs.
  • Adds alerts for mass destroy plans.
  • Records actions and results for the scribe.

AWS, Microsoft & Carrier Support Liaison

  • Opens cases with AWS and Microsoft on recovering deleted resources.
  • Asks about soft delete and backups.
  • Requests guidance on state bucket recovery.
  • Escalates through both TAMs.
  • Records Google Cloud guidance and case numbers.

Business Continuity & Communications

  • Activates continuity for logistics operations and informs leadership.
  • Issues time-stamped updates.
  • Coordinates workarounds and external contacts.
  • Tracks business impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.9 configuration management, 8.32 change management; SOC 2 change management and availability).
  • Assesses infrastructure change integrity.
  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Split large state into smaller workspaces and require plan review for production applies.

Protect locking and test state restore regularly.

Alert on plans that destroy more than a threshold of resources.

Keep soft delete and backups for critical data resources.

Auditors for ISO/IEC 27001:2022 (8.32, 8.9, 8.13) and SOC 2 expect change management and configuration evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on freeze-first response and validated state.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. What did you freeze first?
  2. How did you assess real state?
  3. How did you restore state?
  4. How did you recover the database?
  5. How did you handle orphans?
  6. What would stop this?
  7. How accurate were updates to leadership?
  8. What did the AWS, Microsoft & Carrier Support Liaison add?
  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
