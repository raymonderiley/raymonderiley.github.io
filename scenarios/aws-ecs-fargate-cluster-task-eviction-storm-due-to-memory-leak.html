AWS ECS Fargate Cluster Task Eviction Storm Due to Memory Leak

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines a memory leak released in a new container image that causes ECS Fargate tasks to be killed for out-of-memory conditions. The service scheduler replaces the tasks, the replacements leak and die, and the cluster enters a restart storm that drains capacity, hits throttles on task launches and starves healthy services.

Participants are working-level: container platform engineers, application engineers, application owners, the service desk, cloud operations and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of ECS deployment, circuit breakers, task sizing, health checks and rollback.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Fernhill Payments runs 14 services on an ECS Fargate cluster behind an Application Load Balancer. Services are deployed through a pipeline that performs a rolling update with 100 percent minimum healthy and 200 percent maximum. The deployment circuit breaker is disabled on most services. Tasks are sized at 1 vCPU and 2 GB for the settlement API.

At 11:30 on Wednesday, version 4.18 of the settlement API is deployed. It includes a change that caches unbounded response objects. Memory grows by 40 MB per minute under production traffic. At 11:52, tasks begin exiting with code 137 (OutOfMemoryError). ECS replaces them, new tasks also fail after 45 minutes but the older tasks are killed in rapid sequence as load shifts onto the remaining ones. By 12:20, 70 percent of tasks restart repeatedly, the ALB returns 502, and launch API calls are throttled.

What the team does not yet know: the leak only appears with real payment payload sizes not used in staging, other services share the same subnets which are running low on available IP addresses, the previous task definition revision is still available but the pipeline tags 'latest', and the autoscaling policy adds tasks on CPU, which is low, so capacity does not grow.

Exercise Objectives

  • Recognize a restart storm. Participants read ECS service events, stopped task reasons, MemoryUtilization and ALB target health to identify OOM kills.
  • Roll back or stabilize safely. The team decides between rollback, increasing memory, pinning a previous task definition and reducing traffic, and the order of operations.
  • Protect shared capacity. Engineers prevent the failing service from consuming subnet IPs, API throttles and cluster resources needed by others.
  • Use deployment safety mechanisms. Participants explain circuit breakers, minimum healthy percent and health check grace periods.
  • Handle in-flight payments. The team determines which settlement requests failed, retried or duplicated.
  • Improve release and capacity practice. Participants review load testing, canary deployments, memory limits and alarms.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Reference the specific service, task definition revision or metric when proposing an action.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Task failures and 502 errors lead to declaration.

T+00:30 — Containment. The failing deployment is identified and further deployments are frozen.

T+01:15 — Diagnosis. The OOM cause and the change responsible are confirmed.

T+02:00 — Remediation planning. Rollback and capacity actions are planned.

T+03:00 — Execution. Rollback is executed and shared capacity is protected.

T+04:30 — Stabilization. Tasks stabilize and queues drain.

T+06:00 — Validation. Payment integrity is verified.

T+07:30 — Return to normal and close-out. Normal deployments resume and the incident is closed for debrief.

Injects

Inject #1: Settlement tasks restart repeatedly with exit code 137

Time frame T+00:00 · Variant Primary

Situation

It is 12:25. Merchants report failed settlement submissions. The ALB shows 61 percent 5xx and healthy target count has fallen from 24 to 5. ECS service events show 'task stopped: Essential container in task exited' repeatedly, with stopped reason 'OutOfMemoryError: Container killed due to memory usage'.

The container platform engineer sees 38 restarts per minute for the settlement API and 'unable to place a task' warnings in other services because the subnet has under 20 available IP addresses. CloudWatch MemoryUtilization climbs linearly from 15 percent to 100 percent within 45 minutes of each task start.

The pipeline shows version 4.18 deployed at 11:30 with the circuit breaker disabled. The previous revision (4.17) is registered. The AWS Health Dashboard shows no events.

Facilitator provides: the ECS event log, memory graphs, subnet IP counts and the deployment history.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize a deployment freeze and a rollback decision point.
  • Set the next update at T+00:20.
Container Platform Engineering
  • Identify OOM kills and the shared subnet problem.
  • Plan rollback to 4.17 and enabling the circuit breaker.
  • Cap the failing service while stabilizing.
Application Engineering
  • Confirm the leak pattern and offending change.
  • Explain why more memory only delays failure.
  • Propose the fix path.
Application Owners & Service Desk
  • List in-flight batches and affected merchants.
  • Service desk: issue the holding message.
  • Prepare manual settlement.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Check logs and quotas.
  • List missing alarms.
AWS Support & TAM Liaison
  • Open a case on launch limits.
  • Ask about IP capacity.
  • Record guidance.
Business Continuity & Communications
  • Inform merchant relations.
  • Prepare the first update.
  • Ask for documented RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask how the release was tested.
  • Start the evidence log.

Discussion questions

  1. What tells you this is an OOM kill and not a crash or health check failure?
  2. Why does the restart storm affect other services?
  3. Rollback or add memory: which first and why?
  4. How do you protect other services and subnet IPs while rolling back?
  5. Why did autoscaling not help?
  6. What happened to in-flight settlement requests?
  7. Why was the circuit breaker off?
  8. What do merchants need to be told?

Facilitator notes

  • Do not reveal the subnet IP shortage until the platform engineer checks the other services.
  • If players want to scale up memory, ask what happens at 45 minutes.
  • Look for freeze discipline across all services.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes payment settlement and decides on rollback.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes a deployment freeze across all services.
  • Decides on external notices to merchants.

Container Platform Engineering

  • Reads ECS service events and stopped task reasons, and checks subnet IP availability and API throttling.
  • Plans rollback to the previous task definition and enables the circuit breaker.
  • Protects other services by capping the failing service's desired count.
  • Reviews cluster autoscaling and capacity providers.

Application Engineering

  • Confirms the leak by heap or memory graphs and identifies the offending change.
  • Prepares a fix or a safe configuration setting such as a cache limit.
  • Explains whether increasing memory only delays the problem.
  • Reviews retry and idempotency behavior.

Application Owners & Service Desk

  • Application owners identify payment batches in flight and merchants affected.
  • The service desk logs merchant tickets and issues guidance.
  • Owners prepare manual settlement procedures.
  • Prepare validation tests.

Cloud Operations & Monitoring

  • Builds a dashboard of memory, restarts, healthy targets and 5xx rates per service.
  • Confirms Container Insights and logs are available.
  • Checks AWS Health and Fargate quotas.
  • Adds alarms on task restart rate.

AWS Support & TAM Liaison

  • Opens a case on launch throttling and subnet capacity.
  • Asks about Fargate limits and quota increases.
  • Requests guidance on circuit breaker behavior.
  • Records the guidance.

Business Continuity & Communications

  • Activates continuity for settlement operations and informs merchant relations.
  • Issues time-stamped updates.
  • Coordinates manual processing if needed.
  • Tracks downtime against RTO.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.32 change management; SOC 2 availability and processing integrity).
  • Assesses merchant and card network obligations.
  • Captures evidence for emergency changes.
  • Logs findings on release controls.

Resilience Architect Guidance

Make deployments safe by default. Enable the ECS deployment circuit breaker with rollback, use canary or blue-green releases and pin images by digest rather than mutable tags.

Test like production. Soak tests with realistic payload sizes, memory limits and alarms on memory trend catch leaks before release.

Isolate failure domains. Separate subnets, capacity and API quotas for critical services and plan IP address space for deployment surges.

Make payments idempotent and keep reconciliation tooling ready so retries during restarts do not duplicate settlements.

Auditors for ISO/IEC 27001:2022 (8.32) and SOC 2 expect release testing evidence, rollback capability and change records.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on rollback decisions and release safeguards.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

  5. What happened to in-flight settlements?
  6. How did you freeze deployments?
  7. How did pipeline tags affect the incident?
  8. How were backlogs drained?
  9. How accurate were merchant messages?
  10. What did AWS support add?
  11. What evidence did the scribe capture for auditors?
  12. What testing missed the leak?
  13. What access or permissions were missing?
