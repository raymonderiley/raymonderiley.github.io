Azure Virtual Desktop (AVD) Session Host Pool Registration Failure

Azure Cloud Resiliency

Exercise Overview

This tabletop exercise examines a failure in which Azure Virtual Desktop session hosts cannot register with their host pool. A registration token expires or is rotated incorrectly, newly created or rebooted session hosts show 'Unavailable' or 'No heartbeat', and users get no resources when logging in. A Monday morning logon storm makes the shortage acute.

Participants are working-level: end-user computing and AVD engineers, cloud identity and network engineers, application owners, the service desk, cloud operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of host pool registration, the AVD agent and boot loader, FSLogix, scaling plans and image management.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Eastbrook Financial Services runs 1,800 knowledge workers on pooled AVD host pools in two regions, using FSLogix profile containers on Azure Files, a scaling plan that deallocates hosts at night, and a golden image pipeline. Registration tokens are generated with 30-day expiry by a script run monthly.

At 06:00 on Monday, the scaling plan starts hosts for the working day. Newly started hosts reboot and the AVD agent fails to register because the registration token expired on Sunday and the monthly script failed silently. As hosts fail to register, the pool's available session count drops. By 07:30, only 25 percent of normal capacity is available, and users who connect get 'No resources available'.

What the team does not yet know: a new image rolled out last week updated the agent but also changed a firewall rule that blocks a required URL for 40 hosts, FSLogix profile disks on Azure Files are close to throttling due to the logon storm, the drain mode was set on 200 hosts by an automation, and the secondary region pool is running at reduced capacity.

Exercise Objectives

  • Recognize registration failure. Participants read host pool health, agent logs and event logs to separate registration problems from network, image or capacity issues.
  • Restore capacity quickly. The team issues a new registration token, re-registers hosts and starts additional hosts, including in the secondary region.
  • Control the logon storm. Engineers throttle logons, adjust scaling and protect profile storage.
  • Prioritize users. Participants prioritize trading, customer service and compliance teams over general staff.
  • Avoid compounding changes. The team avoids mass reimaging and uncoordinated host deletion.
  • Improve AVD resilience. Participants review token automation, monitoring, image testing and regional capacity.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • State host counts and session capacity numbers when proposing actions.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. No resources errors and unavailable hosts lead to declaration.

T+00:30 — Containment. Priority users are protected and the logon storm is eased.

T+01:15 — Diagnosis. Registration token and secondary issues are identified.

T+02:00 — Remediation planning. A restore and capacity plan is agreed.

T+03:00 — Execution. Hosts are re-registered and capacity restored.

T+04:30 — Stabilization. Logons normalize and profiles stabilize.

T+06:00 — Validation. Users and applications are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: Monday logon storm with only a quarter of hosts registered

Time frame T+00:00 · Variant Primary

Situation

It is 07:40. Users receive 'No resources available' when connecting. The host pool shows 540 of 720 hosts as 'Unavailable'. The service desk has 900 open tickets and growing.

The AVD engineer finds the registration token expired on Sunday and the monthly script failed silently. Newly started hosts cannot register. The network engineer finds a firewall rule from last week's image rollout blocks a required agent URL on 40 hosts.

FSLogix profile storage on Azure Files shows throttling as users retry. 200 hosts are in drain mode due to an automation. Azure Service Health shows no incident. The trading desk and customer service need access by 08:30.

Facilitator provides: host pool health summary, agent log extract, the script log and the storage metrics.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Set priority user groups and a logon throttle.
  • Set the next update at T+00:20.
End-User Computing & AVD Engineering
  • Generate a new token and re-register hosts.
  • Review drain mode and scaling.
  • Plan staged capacity.
Cloud Identity & Network Engineering
  • Fix the firewall rule and URLs.
  • Check profile storage throttling.
  • Plan logon release.
Application Owners & Service Desk
  • Identify priority groups.
  • Service desk: issue the holding message.
  • Prepare web access to key apps.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Confirm monitoring.
  • List missing alerts.
Microsoft Support & TAM Liaison
  • Open a case.
  • Ask about agent behavior.
  • Record guidance.
Business Continuity & Communications
  • Inform department heads.
  • Prepare the first update.
  • Plan alternate access.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask how the token process is monitored.
  • Start the evidence log.

Discussion questions

  1. How do you tell registration failure from capacity or network problems?
  2. What do you do about the expired token and how fast can hosts re-register?
  3. How do you protect trading and customer service first?
  4. How do you handle the logon storm and profile storage throttling?
  5. Why were 200 hosts in drain mode?
  6. What happens if you reimage hosts en masse?
  7. What alternate access exists for key applications?
  8. What do department heads need to hear?

Facilitator notes

  • Do not reveal the firewall rule until T2 checks agent connectivity.
  • If players reimage everything, ask about time and risk.
  • Look for priority group protection.
  • Time-box to 35 minutes.

  • Assesses regulatory deadlines.
  • Captures evidence of decisions.
  • Logs findings on token management.

Resilience Architect Guidance

Automate and monitor registration: tokens created and rotated by a managed process with expiry alerts, and host pools continuously verified for agent health.

Test images before they reach production: agent connectivity, network rules, FSLogix and a canary host group.

Plan capacity for peak: logon storm tests, profile storage sized for throttling limits and a warm secondary region sized for priority users.

Provide fallback access for critical teams: dedicated pools, web access to key apps and prioritized scaling.

Auditors for ISO/IEC 27001:2022 (8.6, 8.32) and SOC 2 expect capacity management evidence, change testing and monitoring.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on token automation and image testing.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
