AWS DynamoDB Partition Key Hotspotting and Throttle Cascade

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines a DynamoDB table whose partition key design concentrates traffic on a few hot partitions during a product launch. Requests to hot keys are throttled even though the table's total consumed capacity looks well below provisioned throughput, retries amplify load, and dependent services time out.

Participants are working-level: database and data engineers, platform and SRE engineers, application owners, the service desk, cloud operations and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of partition behavior, adaptive capacity, throttling metrics, key design and safe mitigation.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Kestrel Fitness runs a mobile app whose session and workout state is stored in DynamoDB. The main table 'UserActivity' uses a partition key of 'activityDate' (the calendar day) and a sort key of 'userId'. The table runs in provisioned mode with 20,000 write capacity units and autoscaling enabled, and a global secondary index (GSI) on 'challengeId'.

At 07:00 on January 2, a 'New Year Challenge' launches with a push notification. Millions of users log workouts at once. Because every write for the day uses the same partition key, traffic concentrates on a small number of partitions. CloudWatch shows consumed write capacity of 9,000 against 20,000 provisioned, yet WriteThrottleEvents climb and the app returns errors. The GSI on challengeId is hit with a single challenge value, throttling the base table writes as well through back-pressure.

What the team does not yet know: adaptive capacity is helping but cannot keep up with a single-day key, the SDK retry configuration retries throttled writes up to ten times with short delays, the app writes synchronously during workout save so users see failures, and the data model cannot be changed without migrating tables.

Exercise Objectives

  • Recognize hot-partition throttling. Participants compare consumed to provisioned capacity, read throttle metrics and use Contributor Insights to find hot keys.
  • Mitigate without redesign first. The team uses on-demand mode, adjusts capacity, queues writes and reduces retries to stabilize.
  • Protect users and data. Engineers buffer workout writes locally or in a queue so users do not lose activity.
  • Plan a data model fix. Participants evaluate write sharding, composite keys and migration approaches and their risks.
  • Handle GSI back-pressure. The team understands how GSI throttling affects base table writes.
  • Improve capacity and launch practice. Participants review load testing, key design review and alarms.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Use actual DynamoDB behavior; if the group is unsure whether a feature helps with hot partitions, record the question for AWS.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Throttling and app errors lead to declaration.

T+00:30 — Containment. Retry amplification is limited and a buffer is introduced.

T+01:15 — Diagnosis. Contributor Insights confirms the hot key and GSI issue.

T+02:00 — Remediation planning. A mitigation and migration plan is made.

T+03:00 — Execution. Capacity mode, queueing and key changes are applied.

T+04:30 — Stabilization. Throttling falls and queues drain.

T+06:00 — Validation. Data completeness is verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: Throttling despite spare provisioned capacity

Time frame T+00:00 · Variant Primary

Situation

It is 07:25. The app shows 'workout failed to save' for millions of users and social media complaints trend. API error rate is 47 percent. The DynamoDB console shows consumed write capacity at 9,000 WCU versus 20,000 provisioned, but WriteThrottleEvents at 180,000 per minute.

The data engineer enables Contributor Insights and sees one partition key (the date 2027-01-02) accounting for more than 80 percent of write requests. The GSI on challengeId shows heavy throttling for a single challenge value, which also rejects base table writes.

The SDK retries throttled writes ten times, multiplying load. Autoscaling raises capacity slowly, and the AWS Health Dashboard shows no events. Marketing plans a second push notification at 09:00.

Facilitator provides: the metric graphs, the Contributor Insights top keys, the retry configuration and the app save flow.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Decide whether to cancel the second push.
  • Set the next update at T+00:20.
Database & Data Engineering (DynamoDB)
  • Explain why spare capacity does not prevent throttling.
  • Identify the hot key and the GSI back-pressure.
  • Propose immediate mitigations.
Cloud Platform & SRE Engineering
  • Reduce retries and add backoff and jitter.
  • Introduce a write buffer.
  • Check downstream timeouts.
Application Owners & Service Desk
  • Plan local buffering and degraded saves.
  • Service desk: issue the holding message.
  • Prepare messaging.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Enable Contributor Insights.
  • List missing alarms.
AWS Support & TAM Liaison
  • Open a case.
  • Ask about on-demand switching.
  • Record guidance.
Business Continuity & Communications
  • Inform marketing.
  • Prepare the first update.
  • Ask for documented RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask whether key design was reviewed.
  • Start the evidence log.

Discussion questions

  1. How can throttling occur when consumed capacity is below provisioned?
  2. How do you find the hot key and the GSI problem?
  3. What does switching to on-demand do and not do for a single hot key?
  4. How do retries make this worse?
  5. How do you avoid losing workout data?
  6. Should the second push be canceled?
  7. What does a better key design look like?
  8. What do users need to be told?

Facilitator notes

  • Do not reveal the GSI back-pressure until the data engineer inspects GSI metrics.
  • If players only raise capacity, ask why it would not help one key.
  • Look for buffering as the key protection.
  • Time-box to 35 minutes.

Resilience Architect Guidance

Design keys for distribution. A partition key that groups all traffic for a time window creates a hot partition; use high-cardinality keys, write sharding or composite keys, and review key design for every high-volume table.

Treat provisioned capacity as necessary but not sufficient. Alarm on throttle events and use Contributor Insights to watch for skew, and test with realistic key distributions.

Control retries at every layer: SDK backoff with jitter, client behavior, and buffers such as SQS to smooth bursts while protecting durability.

Design GSIs carefully: their key distribution can throttle base table writes.

Auditors for ISO/IEC 27001:2022 (8.6) and SOC 2 expect launch readiness evidence, capacity testing and monitoring.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on key design and retry control.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
