Azure Monitor Agent (AMA) Performance Counter Saturation On-Prem

Hybrid Cloud (Azure Focus)

Exercise Overview

This tabletop exercise examines an Azure Monitor Agent data collection rule that collects high-frequency performance counters and event logs from on-premises servers through Azure Arc, saturating CPU and disk on production hosts and the network link to Azure.

Participants are working-level: observability engineers, Windows and server engineers, application owners, the service desk, cloud operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of data collection rules, sampling rates, agent resource use, throttling, rule assignment scope and rollback.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Redwood Hospital Group runs 900 on-premises Windows servers including clinical applications and imaging. Azure Monitor Agent is deployed through Arc and data collection rules are assigned by tag. A new rule intended for test servers is assigned to a broad tag by mistake.

At 10:00 on Wednesday, a rule collects 200 performance counters every second and all Security and Application event logs. On production servers, the agent consumes 40 percent CPU and heavy disk. Clinical application response times double, the imaging archive stalls and the WAN link to Azure saturates at 95 percent. Monitoring dashboards themselves lag.

What the team does not yet know: removing the rule assignment will take up to 15 minutes to reach agents, restarting agents on clinical servers needs approval, some servers are already degraded to the point that agent updates fail, and the Log Analytics workspace is accruing large cost.

Exercise Objectives

  • Recognize a monitoring-induced outage. Participants correlate agent resource use with application slowness.
  • Remove the cause safely. The team removes the rule assignment and handles propagation delay.
  • Protect clinical systems. Engineers prioritize relief for clinical and imaging servers.
  • Control cost and network load. Participants cut ingestion and relieve the WAN.
  • Avoid making it worse. The team avoids mass restarts without approval.
  • Improve monitoring governance. Participants review rule scope, sampling standards and rollout rings.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Clinical servers are relieved first, and no restart of a clinical server happens without owner approval.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Slow clinical systems and agent load lead to declaration.

T+00:30 — Containment. The rule is removed and clinical servers prioritized.

T+01:15 — Diagnosis. Propagation and residual load are diagnosed.

T+02:00 — Remediation planning. A relief and cost plan is agreed.

T+03:00 — Execution. Agents are relieved in waves.

T+04:30 — Stabilization. Performance returns to baseline.

T+06:00 — Validation. Systems and monitoring are validated.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: Servers slow as the monitoring agent consumes them

Time frame T+00:00 · Variant Primary

Situation

It is 10:30. Clinical applications are slow and the imaging archive stalls. AMA uses 40 percent CPU on many servers and the WAN to Azure is at 95 percent.

The observability engineer finds a data collection rule collecting 200 counters per second and all event logs assigned by a broad tag.

Rule removal takes up to 15 minutes to reach agents. Restarts on clinical servers need approval. Ingestion cost is soaring.

Facilitator provides: rule definition, agent resource graphs, WAN utilization and assignment history.

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize removing the rule.
  • Set the next update at T+00:20.
Observability Engineering (Azure Monitor)
  • Remove assignment.
  • Plan tuned rule.
  • Control cost.
Windows & Server Engineering
  • Find heavy servers.
  • Throttle clinical servers with approval.
  • Validate.
Application Owners & Service Desk
  • Rank clinical servers.
  • Service desk: issue the holding message.
  • Prepare downtime procedures.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Watch cost.
  • Preserve evidence.
Microsoft, Carrier & Vendor Support Liaison
  • Open a case.
  • Ask about disable.
  • Record guidance.
Business Continuity & Communications
  • Inform leadership.
  • Prepare the first update.
  • Plan clinical notice.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about patient safety duties.
  • Start the evidence log.

Discussion questions

  1. How do you prove the agent is the cause?
  2. What is the fastest safe way to relieve clinical servers?
  3. How do you handle propagation delay?
  4. Do you restart agents and who approves?
  5. How do you cut ingestion cost?
  6. How did a test rule reach production?
  7. What do clinicians hear?
  8. What does a safe monitoring rollout look like?

Facilitator notes

  • Do not reveal the broad tag until T1 checks assignments.
  • If players restart all servers, ask about clinical impact.
  • Look for clinical relief first.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes protecting production servers from the monitoring agent itself and sets approval rules for risky changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes emergency changes, exceptions and spend.
  • Decides on stakeholder communications and the end of the incident.

Observability Engineering (Azure Monitor)

  • Removes the rule assignment and monitors propagation.
  • Plans a tuned replacement rule.
  • Controls ingestion and cost.
  • Plans staged assignment.
  • Records actions and results for the scribe.

Windows & Server Engineering

  • Identifies servers with the highest agent load.
  • Stops or throttles agents on clinical servers with approval.
  • Validates application performance.
  • Tracks temporary changes.
  • Records actions and results for the scribe.

Application Owners & Service Desk

  • Application owners rank clinical servers and approve restarts.
  • The service desk logs clinician contacts.
  • Owners prepare downtime procedures.
  • Prepare validation checks.
  • Records actions and results for the scribe.

Cloud Operations & Monitoring

  • Builds a dashboard of agent CPU, WAN usage and application latency.
  • Watches ingestion cost.
  • Preserves evidence.
  • Adds agent resource alerts.
  • Records actions and results for the scribe.

Microsoft, Carrier & Vendor Support Liaison

  • Opens a case on rule propagation and agent throttling.
  • Asks about emergency disable options.
  • Requests guidance on ingestion caps.
  • Escalates through the TAM.
  • Records Google Cloud guidance and case numbers.

Business Continuity & Communications

  • Activates continuity for clinical operations and informs leadership.
  • Issues time-stamped updates.
  • Coordinates workarounds and external contacts.
  • Tracks business impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.16 monitoring, 8.32 change management; SOC 2 availability).
  • Assesses patient safety and clinical system availability.
  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Roll out monitoring configuration in rings, starting with test servers, and scope assignments narrowly.

Set sampling standards and agent resource limits for production, especially clinical systems.

Alert on agent CPU, disk and network use.

Protect WAN capacity for clinical traffic.

Auditors for ISO/IEC 27001:2022 (8.16, 8.32) and SOC 2 expect monitoring and change control evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on staged rollout of monitoring and clinical protection.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How did you link slowness to the agent?
  2. What did you relieve first?
  3. How did you handle propagation?
  4. How did you handle restarts?
  5. How did you control cost?
  6. How did you handle downtime procedures?
  7. How accurate were updates to leadership?
  8. What did the Microsoft, Carrier & Vendor Support Liaison add?
  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
