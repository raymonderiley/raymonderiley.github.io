Azure Firewall Premium Rule Engine CPU Starvation

Azure Cloud Resiliency

Exercise Overview

This tabletop exercise examines an Azure Firewall Premium instance that suffers CPU starvation after TLS inspection and IDPS signatures are enabled broadly. Latency rises, throughput collapses, connections time out across hub-and-spoke traffic, and the firewall's autoscale cannot keep up with the spike.

Participants are working-level: cloud network security engineers, cloud platform and SRE engineers, application owners, the service desk, security operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of firewall throughput metrics, rule processing order, TLS inspection costs, IDPS modes and safe bypass.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Hollis Pharmaceuticals routes all spoke-to-spoke, spoke-to-internet and on-premises traffic through a single Azure Firewall Premium in a hub VNet. Network rules, application rules and IDPS in alert-and-deny mode are configured. TLS inspection was enabled for outbound web traffic last week for a data loss prevention project.

At 09:30 on Thursday, a clinical trial data transfer begins moving 6 TB to a partner through the firewall, while the morning peak of user traffic starts. Firewall throughput metrics show CPU at 95 to 100 percent, SNAT port use rising and latency from 5 ms to 900 ms. Health probes from load balancers through the firewall fail intermittently and applications in spokes report timeouts. An engineer added 40 new application rules at 09:15 using wildcard FQDNs, increasing rule evaluation cost.

What the team does not yet know: TLS inspection decrypts the transfer, which is the main CPU consumer, the IDPS signature set was expanded in the last update, a forced tunneling route sends internet-bound traffic via on-premises first for some spokes, and there is no secondary firewall or bypass path approved for critical workloads.

Exercise Objectives

  • Recognize firewall CPU and throughput starvation. Participants read firewall metrics (throughput, latency probe, SNAT utilization, CPU) and logs to separate load from outage.
  • Reduce load safely. The team pauses the bulk transfer, scopes TLS inspection down, and tunes IDPS without leaving blind spots.
  • Protect critical traffic. Engineers prioritize clinical and manufacturing flows and consider controlled bypass or alternate paths.
  • Make rule changes carefully. Participants avoid large rule edits during the incident and apply a peer-reviewed rollback.
  • Assess security risk of relaxations. The team documents each temporary exception and monitors compensating controls.
  • Improve firewall architecture. Participants review sizing, TLS inspection scope, rule hygiene and redundancy.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Each relaxation of inspection or filtering must be recorded with owner, scope, expiry and compensating control.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Timeouts and firewall CPU alerts lead to declaration.

T+00:30 — Containment. The bulk transfer is paused and critical flows protected.

T+01:15 — Diagnosis. Load drivers are identified.

T+04:30 — Stabilization. CPU and latency stabilize.

T+06:00 — Validation. Applications and security posture are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: Firewall CPU saturates and spokes time out

Time frame T+00:00 · Variant Primary

Situation

It is 09:55. Applications across spokes report timeouts. Azure Firewall metrics show throughput near its limit, CPU at 98 percent and latency probe at 900 ms. SNAT utilization is at 85 percent.

The network security engineer finds a 6 TB clinical trial transfer to a partner running through TLS inspection, 40 wildcard application rules added at 09:15 and an expanded IDPS signature set. Some spokes use forced tunneling via on-premises.

There is no approved bypass for critical workloads and no secondary firewall. Azure Service Health shows no incident. Manufacturing line systems also depend on the firewall.

Facilitator provides: firewall metrics, top flows, rule change history and the route table summary.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize pausing the bulk transfer.
  • Set the next update at T+00:20.
Cloud Network Security Engineering (Azure Firewall)
  • Identify load drivers and rule hit counts.
  • Plan TLS exclusions and IDPS tuning.
  • Plan bypass with compensating controls.
Cloud Platform & SRE Engineering
  • Pause the transfer and check routes.
  • Prepare alternative paths.
  • Validate flows.
Application Owners & Service Desk
  • Rank flows and find the transfer owner.
  • Service desk: issue the holding message.
  • Prepare degraded modes.
Security Operations & Monitoring
  • Monitor for threats.
  • Review alerts.
  • Preserve logs.
Microsoft Support & TAM Liaison
  • Open a case.
  • Ask about autoscale.
  • Record guidance.
Business Continuity & Communications
  • Inform department leads.
  • Prepare the first update.
  • Plan manual alternatives.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about rule approvals.
  • Start the evidence log.

Discussion questions

  1. How do you tell CPU starvation from a routing or outage problem?
  2. What is consuming firewall capacity and how do you prove it?
  3. Which relaxation is safest: pause the transfer, scope TLS inspection or change IDPS mode?
  4. How do you protect manufacturing and clinical flows?
  5. What does a bypass path require to be acceptable?
  6. Why were 40 rules added during peak hours?
  7. How do you record exceptions for audit?
  8. What do departments need to hear?

Facilitator notes

  • Do not reveal the wildcard rule cost until T1 reviews rule hits.
  • If players disable the firewall entirely, ask about risk.
  • Look for pausing the transfer as the first lever.
  • Time-box to 35 minutes.

Resilience Architect Guidance

Size and scope inspection deliberately: TLS inspection and IDPS only where the risk justifies the cost, with capacity tested against peak plus bulk transfers.

Keep rules clean and changes safe: avoid wildcard sprawl, use rule collections with ownership and apply changes in small batches outside peak hours with automatic rollback.

Provide architectural escape routes: approved, monitored alternative paths for critical flows and a documented process for temporary exceptions with expiry.

Alert on throughput, CPU and SNAT utilization well before limits.

Auditors for ISO/IEC 27001:2022 (8.20, 8.32) and SOC 2 expect capacity evidence, change control and recorded exceptions.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on inspection scope and recorded exceptions.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did you identify firewall CPU as the cause?
  2. What consumed capacity and how did you prove it?
  3. How did you decide between the relaxations?
  4. How did you protect clinical and manufacturing flows?
  5. How did you handle the partner deadline?
  6. How were exceptions recorded?
  7. How did rule changes affect the incident?
  8. How was SNAT handled?
  9. How accurate were updates to leadership?
  10. What did Microsoft support add?
  11. What evidence did the scribe capture for auditors?
  12. How is firewall capacity tested?
  13. What access or permissions were missing?
  14. What alerts are missing?
  15. What would you change in firewall design?
