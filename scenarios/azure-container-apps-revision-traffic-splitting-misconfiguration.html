Azure Container Apps Revision Traffic Splitting Misconfiguration

Azure Cloud Resiliency

Exercise Overview

This tabletop exercise examines an Azure Container Apps release in which a traffic split between revisions is misconfigured, sending 100 percent of production traffic to a new revision that has a broken database migration, while the healthy previous revision is deactivated by a cleanup rule.

Participants are working-level: container platform engineers, application engineers, application owners, the service desk, cloud operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of revision modes, traffic weights, labels, probes, scale rules, schema compatibility and safe rollback.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Wren Retail runs its order API on Azure Container Apps in multiple revision mode. A release pipeline was meant to send 10 percent of traffic to the new revision for 30 minutes, then promote. The same pipeline includes a cleanup step that deactivates all but the latest two revisions.

At 13:10 on Monday, a pipeline variable error sets the new revision's traffic weight to 100. The new revision runs a forward-only database migration that dropped a column still used by the previous version. Readiness probes pass because they check only a shallow endpoint. By 13:25, order submission errors reach 60 percent. The cleanup step has already deactivated the revision from two releases ago, and the previous revision is still active but scaled to zero by an idle rule.

What the team does not yet know: rolling traffic back to the previous revision will fail because it reads the dropped column, a database backup exists from 06:00 but orders have been written since, a feature flag can disable the new code path but only after a redeploy, and some in-flight orders are stuck in a half-complete state.

Exercise Objectives

  • Recognize a release failure. Participants correlate revision traffic, error rates and migration history to see the release is the cause.
  • Choose a safe remediation. The team weighs rollback, forward-fix and feature flag options against schema incompatibility.
  • Protect data integrity. Engineers avoid restoring a stale backup over new orders and reconcile half-complete orders.
  • Control traffic. Participants use traffic weights, labels and scale settings deliberately and verify each change.
  • Communicate with customers. The team provides accurate status for order failures and handles stuck orders.
  • Improve release resilience. Participants review expand-contract migrations, deep health probes, canary gates and cleanup rules.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Do not restore a database backup over production without a data reconciliation plan for newer orders.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Order errors and the traffic setting lead to declaration.

T+00:30 — Containment. Bleeding is reduced and the cause is confirmed.

T+01:15 — Diagnosis. Schema and data impact are diagnosed.

T+02:00 — Remediation planning. A forward-fix or rollback plan is agreed.

T+03:00 — Execution. The fix is applied and traffic is restored carefully.

T+04:30 — Stabilization. Errors fall and orders flow.

T+06:00 — Validation. Stuck orders are reconciled.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: Full traffic on a broken revision

Time frame T+00:00 · Variant Primary

Situation

It is 13:30. Order submission errors are at 60 percent. Container Apps shows the new revision at 100 percent traffic. The release was meant to be a 10 percent canary.

The platform engineer finds a pipeline variable error and a cleanup step that deactivated an older revision. The previous revision is active but scaled to zero. Readiness probes are shallow and passing.

The application engineer reports the new release's migration dropped a column the previous version reads, so rollback will fail. A 06:00 backup exists but newer orders have been written. Some orders are stuck half-complete.

Facilitator provides: revision list, traffic settings, migration script, error samples and the pipeline log.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Decide whether to pause order-taking.
  • Set the next update at T+00:20.
Container Platform Engineering (Container Apps)
  • Check revisions and traffic.
  • Plan safe traffic changes.
  • Fix the cleanup rule.
Application Engineering
  • Analyze migration compatibility.
  • Prepare a forward-fix.
  • Plan reconciliation.
Application Owners & Service Desk
  • Rank flows.
  • Service desk: issue the holding message.
  • Prepare manual order capture.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Check the database.
  • Preserve logs.
Microsoft Support & TAM Liaison
  • Open a case.
  • Ask about traffic and scale.
  • Record guidance.
Business Continuity & Communications
  • Inform leadership.
  • Prepare the first update.
  • Plan manual capture.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about lost orders.
  • Start the evidence log.

Discussion questions

  1. How do you confirm the release is the cause?
  2. Why will rolling traffic back not simply fix this?
  3. What are the forward-fix and backup restore options and their risks?
  4. How do you handle half-complete orders?
  5. Do you pause order-taking and for how long?
  6. What do customers need to hear?
  7. How did the pipeline set 100 percent traffic and remove a rollback target?
  8. Why did probes pass on a broken revision?

Facilitator notes

  • Do not reveal the dropped column until T2 reviews the migration.
  • If players restore the backup, ask about newer orders.
  • Look for protecting data first.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes stopping failed orders and protecting data and sets approval for schema changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes rollback or forward-fix.
  • Decides on customer messaging.

Container Platform Engineering (Container Apps)

  • Checks revision status, traffic weights and scale rules.
  • Reactivates or redeploys revisions and sets labels.
  • Plans safe traffic shifts.
  • Fixes the cleanup rule.

Application Engineering

  • Analyzes the migration and compatibility with both versions.
  • Prepares a forward-fix such as restoring the column or a compatibility view.
  • Plans reconciliation of half-complete orders.
  • Validates order flow.

Application Owners & Service Desk

  • Application owners rank flows and support order recovery.
  • The service desk logs customer contacts.
  • Owners decide on temporary order-taking limits.
  • Prepare validation tests.

Cloud Operations & Monitoring

  • Builds a dashboard of revision traffic, errors and order throughput.
  • Checks database metrics.
  • Preserves logs and migration history.
  • Adds deep probe and canary alerts.

Microsoft Support & TAM Liaison

  • Opens a Sev A case on revision behavior and scale rules.
  • Asks about traffic weight application and reactivation.
  • Requests guidance on probes.
  • Records guidance.

Business Continuity & Communications

  • Activates continuity for order handling and informs leadership.
  • Issues time-stamped updates.
  • Coordinates manual order capture.
  • Tracks impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.32 change management; SOC 2 processing integrity and availability).
  • Assesses consumer obligations on lost orders.
  • Captures evidence of release controls.
  • Logs findings on testing.

Resilience Architect Guidance

Make releases reversible: expand-contract migrations so old and new versions both work, destructive changes only in a later, separate release.

Make traffic shifts safe: automated canary gates driven by deep health checks and business metrics, with traffic weights validated before apply.

Keep rollback targets: retain recent revisions, avoid scale-to-zero for the previous version during a release window.

Design probes that test dependencies, not only the process.

Auditors for ISO/IEC 27001:2022 (8.32) and SOC 2 expect change testing and release approval evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on reversible migrations and canary gates.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did you link errors to the revision?
  2. Why did rollback fail?
  3. How did you weigh forward-fix and restore?
  4. How were half-complete orders handled?
  5. Did you pause order-taking?
  6. How did you handle the flag option?
  7. How were customers and media handled?
  8. How was cold start handled?
  9. How accurate were updates to leadership?
  10. What did Microsoft support add?
  11. What evidence did the scribe capture for auditors?
  12. How are migrations designed?
  13. What access or permissions were missing?
  14. What alerts are missing?
  15. What would you change in the release process?
