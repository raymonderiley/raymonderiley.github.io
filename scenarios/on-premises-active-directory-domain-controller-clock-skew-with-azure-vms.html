On-Premises Active Directory Domain Controller Clock Skew with Azure VMs

Hybrid Cloud (Azure Focus)

Exercise Overview

This tabletop exercise examines a domain controller holding the time role that drifts after a failed time source and a virtualization host sync, so Kerberos tickets fail for Azure VMs and cloud-joined services, authentication breaks across the hybrid estate and logs show inconsistent timestamps.

Participants are working-level: directory services engineers, cloud platform engineers, application owners, the service desk, security operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of the PDC emulator time role, Kerberos skew tolerance, host time sync, Azure VM time sources and log correlation.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Hartwell Energy runs Active Directory with its PDC emulator on a virtual machine on-premises. Azure VMs join the domain and use the domain hierarchy for time. The upstream NTP source was a single appliance that failed last week. Hypervisor time sync is enabled on the PDC emulator VM.

At 06:45 on Friday, the PDC emulator drifts 11 minutes ahead after a host time sync conflict. Kerberos fails for any client beyond five minutes of skew. Azure VMs, file shares and SQL services report authentication errors. Service accounts fail, scheduled jobs stop and administrators cannot sign in to some servers. SIEM correlation across systems breaks because of timestamp differences.

What the team does not yet know: some systems are ahead and some behind, a sudden time correction can break replication or invalidate tickets, certificate validity checks are affected, and a security team suspects tampering.

Exercise Objectives

  • Recognize time skew. Participants identify the skew pattern across domain, hosts and cloud VMs.
  • Correct time safely. The team fixes the authoritative source and steps or slews time carefully.
  • Restore authentication. Engineers restore Kerberos function and service accounts.
  • Preserve evidence integrity. Participants record skew periods for log correlation.
  • Rule out tampering. The team distinguishes drift from malicious change.
  • Improve time architecture. Participants review time sources, host sync settings and monitoring.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Record the measured offset of each key system before and after correction.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Authentication failures and skew lead to declaration.

T+00:30 — Containment. The time source is fixed and priority set.

T+01:15 — Diagnosis. Skew and impact are diagnosed.

T+02:00 — Remediation planning. A correction and recovery plan is agreed.

T+03:00 — Execution. Time is corrected in order.

T+04:30 — Stabilization. Authentication stabilizes.

T+06:00 — Validation. Services and logs are validated.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Resilience Architect Guidance

Configure multiple reliable upstream time sources for the PDC emulator and disable conflicting hypervisor sync.

Set a consistent time standard for Azure VMs.

Alert on offset between domain controllers and key systems.

Record and map skew periods for log correlation.

Auditors for ISO/IEC 27001:2022 (8.17 clock synchronization, 8.15) and SOC 2 expect time synchronization and log integrity evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on measured offsets and safe correction.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

  3. How did you correct time?

  7. How accurate were updates to leadership?

  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
