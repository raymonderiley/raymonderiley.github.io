Azure Front Door Global Routing Table Corruption

Azure Cloud Resiliency

Exercise Overview

This tabletop exercise examines a global routing problem on Azure Front Door in which a configuration push leaves routing rules inconsistent across edge locations. Some users reach the correct origins, others receive 404 or 503 errors, and still others are routed to the wrong backend, including a staging origin.

Participants are working-level: edge and Front Door engineers, cloud network and DNS engineers, application owners, the service desk, cloud operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of Front Door routes, origin groups, health probes, rules engines, WAF policies and bypass paths.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Marigold Bank serves its public website, mobile API and partner API through one Azure Front Door Premium profile with origin groups in two regions and a staging origin used for pre-release checks. Routes are managed by Terraform with a pipeline that applies changes globally. DNS CNAMEs point to the Front Door endpoints; origins can also be reached directly by IP.

At 15:00 on Wednesday, a pipeline run updates route patterns, rules engine actions and origin priorities. Front Door's configuration propagation takes several minutes and some edge locations pick up a partially applied state, where the '/api/*' route points to the staging origin group for some POPs. By 15:20, customers in some regions see 404 on login, the mobile API occasionally returns staging data, and partner API calls fail with 503.

What the team does not yet know: a rules engine redirect has a typo that rewrites '/api' paths, staging returns test accounts that are mixed with production sessions for some users, health probes mark the primary origin degraded because probe paths changed, and rolling back via the pipeline requires another global propagation that takes 10 to 20 minutes.

Exercise Objectives

  • Recognize inconsistent global routing. Participants compare behavior across regions, review Front Door metrics and diagnostics to see mixed routing.
  • Stop exposure of staging and test data. The team prevents users from reaching the staging origin and checks for data crossing environments.
  • Choose a safe rollback. Engineers decide between pipeline rollback, portal edit, disabling routes and DNS bypass, understanding propagation delays.
  • Maintain service for critical flows. Participants use a direct origin or Traffic Manager bypass for login and partner APIs.
  • Check security impact. The team assesses WAF coverage during bypass and any data exposure.
  • Improve release practice. Participants review staged rollout, validation and rollback for edge configuration.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Specify the route, origin group or rule involved in every action and state the propagation delay you expect.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Regional 404s, 503s and mixed data reports lead to declaration.

T+00:30 — Containment. Pipeline is frozen and staging exposure is blocked.

T+01:15 — Diagnosis. The faulty route and rule are identified.

T+02:00 — Remediation planning. A rollback and bypass plan is agreed.

T+03:00 — Execution. Rollback is applied and bypass paths used for critical flows.

T+04:30 — Stabilization. Edge locations converge and errors fall.

T+06:00 — Validation. Data crossing and service health are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: Mixed 404, 503 and staging responses across regions

Time frame T+00:00 · Variant Primary

Situation

It is 15:25. Customers in Europe report login 404 errors while customers in North America sometimes see test account data after login. Partner APIs return 503. Synthetic checks from different regions show different results.

The edge engineer finds the '/api/*' route pointed to the staging origin group in some POPs and a rules engine rewrite typo. Health probes on the primary origin report degraded because probe paths changed.

The pipeline pushed the change at 15:00 and propagation is still in progress. Rollback through the pipeline needs another 10 to 20 minutes. Azure Service Health shows no incident. The staging origin is publicly reachable.

Facilitator provides: route and rule diffs, status code distribution by region, origin health and the pipeline log.

  • Declare the incident and name the technical lead and scribe.
  • Freeze edge changes and lock the pipeline.
  • Set the next update at T+00:20.
Edge & Front Door Engineering
  • Identify the faulty route and rule.
  • Plan rollback and block staging.
  • Check probes and WAF.
Cloud Network & DNS Engineering
  • Plan a bypass for critical flows.
  • Consider TTL and caching.
  • Check direct origin exposure.
Application Owners & Service Desk
  • Identify affected flows and sessions.
  • Service desk: issue the holding message.
  • Check data crossing.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Run synthetic checks.
  • List missing alarms.
Microsoft Support & TAM Liaison
  • Open a case.
  • Ask about rollback timing.
  • Record guidance.
Business Continuity & Communications
  • Inform branches.
  • Prepare the first update.
  • Ask for RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask who approved the change.
  • Start the evidence log.

Discussion questions

  1. How do you tell inconsistent routing from an origin outage?
  2. Why are users hitting staging and what is the exposure?
  3. What are your rollback options and their propagation delays?
  4. How do you keep login working during propagation?
  5. What does bypassing Front Door do to WAF protection?
  6. How do you check for data crossing between environments?
  7. Why did the pipeline apply globally in one step?
  8. What do customers and partners need to hear?

Facilitator notes

  • Do not reveal the staging data crossing until APP checks sessions.
  • If players bypass with no WAF, ask about risk.
  • Look for freeze first.
  • Time-box to 35 minutes.

  • Logs findings on release controls.

Resilience Architect Guidance

Treat edge configuration as production code: staged rollout with canary routes, automated validation from multiple regions and a tested rollback that accounts for propagation time.

Keep staging off the internet: origins accept traffic only from Front Door (private link or header and IP restrictions), and staging never shares routes with production.

Prepare bypass paths with controls: a documented DNS or Traffic Manager route with WAF-equivalent protections and approval.

Monitor with synthetic checks per region and alarm on status code and origin health divergence.

Auditors for ISO/IEC 27001:2022 (8.31, 8.32) and SOC 2 expect environment separation, change control and tested rollback.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on staged rollout and environment separation.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
