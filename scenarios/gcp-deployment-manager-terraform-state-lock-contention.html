GCP Deployment Manager / Terraform State Lock Contention

Google Cloud Resiliency

Exercise Overview

This tabletop exercise examines a Terraform state lock contention in which multiple pipelines hold or fight over a remote state lock stored in a Cloud Storage backend, blocking an emergency infrastructure change while a forced unlock risks state corruption and drift.

Participants are working-level: infrastructure as code engineers, platform and SRE engineers, application owners, release managers, cloud operations and monitoring staff, the Google Cloud support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of state locks, remote backends, plan and apply separation, drift detection, state recovery and emergency change.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Foxglove Logistics manages 300 projects of infrastructure with Terraform and some legacy Deployment Manager templates. State files are stored in Cloud Storage buckets with object versioning and locks. A single large state file covers shared networking and firewall rules and is applied by several pipelines.

At 09:30 on Wednesday, an apply job crashes mid-run leaving the state lock held. Other pipelines queue. An emergency change to widen a load balancer capacity setting for a live incident is blocked. A second engineer forces unlock and runs apply from a laptop while a scheduled pipeline also applies. The state file is written twice, some resources show in state that no longer exist and the plan shows destroying several firewall rules.

What the team does not yet know: object versioning has earlier state versions, the laptop apply used outdated provider versions, drift exists between code and live resources, and the destroy plan would remove rules that production depends on.

Exercise Objectives

  • Recognize lock contention and state risk. Participants read lock info, state versions and plans to see what is safe.
  • Protect production. The team avoids applying a destructive plan and preserves live resources.
  • Recover state. Engineers restore a known good state version and reconcile drift carefully.
  • Deliver the emergency change safely. Participants use a minimal, targeted change with review.
  • Control access. The team stops uncoordinated applies and limits who can force unlock.
  • Improve IaC resilience. Participants review state partitioning, locking, drift detection and emergency paths.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Do not run apply with a plan that destroys resources until the plan has been reviewed line by line by a second person.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Blocked changes and a risky plan lead to declaration.

T+00:30 — Containment. Applies are frozen and the emergency path is chosen.

T+01:15 — Diagnosis. State damage and drift are diagnosed.

T+02:00 — Remediation planning. A state recovery and change plan is agreed.

T+03:00 — Execution. State is recovered and the emergency change applied.

T+04:30 — Stabilization. Pipelines are re-enabled in order.

T+06:00 — Validation. Drift and integrity are validated.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: State lock stuck and a destructive plan appears

Time frame T+00:00 · Variant Primary

Situation

It is 10:30. A load balancer capacity fix is blocked by a state lock. A forced unlock and a laptop apply have just happened. The next plan shows destroying six firewall rules.

The IaC engineer finds two concurrent writes to the state and a stale provider version.

Object versioning keeps earlier state. Drift exists between code and live resources. A live incident needs the capacity fix.

Facilitator provides: lock metadata, state version list, plan output and audit logs.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Freeze all applies.
  • Set the next update at T+00:20.
Infrastructure as Code Engineering
  • Inspect state versions.
  • Plan restore.
  • Plan import.
Platform & SRE Engineering
  • Review plan.
  • Prepare targeted change.
  • Check providers.
Application Owners & Release Management
  • Rank the emergency fix.
  • Service desk: issue the holding message.
  • Hold other changes.
Cloud Operations & Monitoring
  • Monitor production.
  • Review audit logs.
  • Preserve evidence.
Google Cloud Support & TAM Liaison
  • Open a case.
  • Ask about versions.
  • Record guidance.
Business Continuity & Communications
  • Inform leadership.
  • Prepare the first update.
  • Plan stakeholder contact.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about change control.
  • Start the evidence log.

Discussion questions

  1. How do you decide whether the state can be trusted?
  2. Why is the destroy plan dangerous and how do you stop it?
  3. How do you deliver the emergency fix without a full apply?
  4. What does a forced unlock risk?
  5. How do you restore a state version?
  6. How do you handle drift?
  7. Who may force unlock and apply?
  8. What do leaders hear?

Facilitator notes

  • Do not reveal the stale provider until T2 checks versions.
  • If players apply the plan to unblock, stop and discuss.
  • Look for freezing first.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes delivering the emergency infrastructure fix and sets approval rules for risky changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes emergency changes, exceptions and spend.
  • Decides on stakeholder communications and the end of the incident.

Infrastructure as Code Engineering

  • Freezes applies and inspects lock metadata and state versions.
  • Restores a known good state version.
  • Plans import or refresh for drift.
  • Plans partitioning of state.
  • Records actions and results for the scribe.

Platform & SRE Engineering

  • Reviews the plan and prevents destroys.
  • Applies a targeted change for the emergency fix.
  • Checks provider versions.
  • Validates production resources.
  • Records actions and results for the scribe.

Application Owners & Release Management

  • Application owners rank the emergency fix and dependent services.
  • Release managers hold unrelated changes.
  • The service desk logs impacts.
  • Prepare validation checks.
  • Records actions and results for the scribe.

Cloud Operations & Monitoring

  • Monitors production for changes and unexpected deletions.
  • Reviews audit logs of who applied what.
  • Preserves evidence.
  • Adds alerts for state writes.
  • Records actions and results for the scribe.

Google Cloud Support & TAM Liaison

  • Opens a case on bucket object versions and locking behavior.
  • Asks about recovery of state objects.
  • Requests guidance on audit logs.
  • Escalates through the TAM.
  • Records Google Cloud guidance and case numbers.

Business Continuity & Communications

  • Activates continuity for platform delivery and informs leadership.
  • Issues time-stamped updates.
  • Coordinates workarounds and external contacts.
  • Tracks business impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.9 configuration management, 8.32 change management; SOC 2 change management and availability).
  • Assesses change control and configuration integrity.
  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Partition state by blast radius and ownership so one failed job cannot block everything.

Restrict forced unlock and manual applies, require plan review for destroys and run drift detection regularly.

Keep state buckets versioned and test recovery.

Provide an emergency change path with review and logging.

Auditors for ISO/IEC 27001:2022 (8.32, 8.9 configuration management) and SOC 2 expect change control and configuration evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on state recovery and safe emergency change.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How did you assess state trust?
  2. How did you stop a destructive plan?
  3. How did you deliver the emergency fix?
  4. How did you restore state?
  5. How did you handle drift?
  6. How did you re-enable pipelines?
  7. How accurate were updates to leadership?
  8. What did the Google Cloud Support & TAM Liaison add?
  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
