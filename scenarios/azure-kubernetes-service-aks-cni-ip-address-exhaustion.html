Azure Kubernetes Service (AKS) CNI IP Address Exhaustion

Azure Cloud Resiliency

Exercise Overview

This tabletop exercise examines an AKS cluster using Azure CNI whose node subnet runs out of IP addresses during a scale-out. New Pods stay in ContainerCreating, node upgrades and autoscaling fail, and the cluster cannot recover capacity because each node pre-allocates a block of IPs from the same exhausted subnet.

Participants are working-level: Kubernetes platform engineers, cloud network engineers, application owners, the service desk, cloud operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of Azure CNI IP allocation, maxPods, subnet sizing, surge upgrades and recovery options.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Linden Retail runs its storefront on an AKS cluster with Azure CNI (non-overlay) in a /22 subnet (about 1,019 usable addresses) with maxPods set to 110 and 30 nodes. Each node reserves up to 110 IPs for Pods. A cluster autoscaler can add up to 40 nodes, and a node pool upgrade uses a surge of 33 percent.

At 10:00 on a promotion day, the cluster autoscaler adds nodes as traffic grows. Each new node claims its IP block, and the subnet is exhausted at 36 nodes. New nodes join but cannot assign Pod IPs: Pods hang in ContainerCreating with 'failed to allocate for range 0: no IP addresses available'. At the same time, a scheduled node image upgrade begins and creates surge nodes that further consume IPs, leaving some existing nodes cordoned.

What the team does not yet know: other services share the subnet and consume addresses, a prior test cluster left unused network interfaces, scaling down nodes releases IPs slowly, and the subnet cannot be resized in place.

Exercise Objectives

  • Recognize CNI IP exhaustion. Participants read Pod events, node status, subnet utilization and CNI logs to confirm exhaustion rather than a scheduling or image problem.
  • Stop the upgrade and autoscaling. The team halts surge upgrades and caps scale-out to avoid worsening the shortage.
  • Free or add addresses. Engineers delete unused NICs, reduce maxPods through new node pools or add a larger subnet with a new node pool.
  • Protect the storefront. Participants shed load, protect critical services and prioritize Pods.
  • Plan migration. The team evaluates moving to Azure CNI Overlay or a larger subnet and the migration path.
  • Improve capacity design. Participants review subnet sizing, IP planning and alarms.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • State the number of IPs per node and nodes when you reason about capacity.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Pending Pods and failed scale-out lead to declaration.

T+00:30 — Containment. Upgrades and scale-out are paused and priorities set.

T+01:15 — Diagnosis. IP exhaustion and consumers are identified.

T+02:00 — Remediation planning. A free-space and migration plan is agreed.

T+03:00 — Execution. Addresses are freed and a new node pool is added.

T+04:30 — Stabilization. Pods schedule and the cluster stabilizes.

T+06:00 — Validation. Services and scaling are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: Pods stuck in ContainerCreating during the promotion

Time frame T+00:00 · Variant Primary

Situation

It is 10:35. Checkout latency is rising and 140 Pods are stuck in ContainerCreating with 'no IP addresses available'. The autoscaler shows 36 nodes and new nodes are NotReady for networking.

The platform engineer sees a node image upgrade running with surge nodes. The network engineer finds the node subnet at 99 percent utilization and 40 orphaned network interfaces from a deleted test cluster in the same subnet.

Azure Service Health shows no events. Each node reserves up to 110 IPs. The promotion peak is expected in 90 minutes.

Facilitator provides: Pod event samples, subnet utilization, node pool settings and the orphaned NIC list.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize pausing the upgrade and capping autoscaling.
  • Set the next update at T+00:20.
Kubernetes Platform Engineering (AKS)
  • Stop the upgrade and cap the autoscaler.
  • Explain IP allocation per node.
  • Plan a new node pool.
Cloud Network Engineering
  • Measure subnet use and find consumers.
  • Plan safe cleanup of orphaned NICs.
  • Plan a larger subnet.
Application Owners & Service Desk
  • Rank workloads.
  • Service desk: issue the holding message.
  • Plan degraded modes.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Confirm alerts.
  • List missing alarms.
Microsoft Support & TAM Liaison
  • Open a case.
  • Ask about overlay.
  • Record guidance.
Business Continuity & Communications
  • Inform merchandising.
  • Prepare the first update.
  • Ask for RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask whether IP planning was reviewed.
  • Start the evidence log.

Discussion questions

  1. How do you confirm IP exhaustion rather than another cause?
  2. Why did the upgrade and autoscaler make it worse?
  3. How do you free addresses quickly and safely?
  4. Can the subnet be resized and what is the alternative?
  5. How do you protect checkout meanwhile?
  6. What happens to existing nodes during cordon and drain?
  7. What do merchandising and leadership need to hear?
  8. Why were orphaned NICs there?

Facilitator notes

  • Do not reveal the orphaned NICs until T2 inspects the subnet.
  • If players add nodes, ask where the IPs come from.
  • Look for stopping the upgrade first.
  • Time-box to 35 minutes.

Resilience Architect Guidance

Plan IP address space as capacity. With Azure CNI, size subnets for maximum nodes times maxPods plus upgrade surge, or choose CNI Overlay so Pods do not consume VNet addresses.

Control surge and scale: cap autoscaler maximums to subnet capacity, test upgrade surge and use PodDisruptionBudgets so drains are safe.

Keep IP hygiene: automated detection of orphaned network interfaces, IPAM and alarms on subnet utilization.

Prepare an escape route: a pre-approved procedure for creating a new node pool in a larger subnet.

Auditors for ISO/IEC 27001:2022 (8.6) and SOC 2 expect capacity planning evidence and tested operational procedures.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on IP planning and stopping upgrades under pressure.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
