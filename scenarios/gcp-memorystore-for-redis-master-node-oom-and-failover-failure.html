GCP Memorystore for Redis Master Node OOM and Failover Failure

Google Cloud Resiliency

Exercise Overview

This tabletop exercise examines a Memorystore for Redis standard-tier instance whose primary runs out of memory after a key growth bug, a failover then fails to complete cleanly, sessions are lost and the origin database is hit by a surge of cache misses.

Participants are working-level: platform engineers, application engineers, application owners, the service desk, cloud operations and monitoring staff, the Google Cloud support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of eviction policies, memory sizing, failover, persistence limits, stampede protection and cache warm-up.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Linden Travel uses a standard-tier Memorystore Redis instance of 32 GB for user sessions, search results and rate counters. The eviction policy is noeviction for session safety. The database behind it handles about 15 percent of reads when the cache is warm.

At 14:00 on Friday, a release stores unbounded search result lists without expiry. Memory reaches 100 percent at 14:40. With noeviction, writes fail with OOM errors, logins fail and the primary becomes unresponsive. Automatic failover starts at 14:50 but the replica also holds a near-full dataset and takes long to become writable. When it does, much session data is missing. Traffic floods the database with cache misses and database CPU reaches 95 percent.

What the team does not yet know: flushing search keys would free memory but sessions are mixed in the same keyspace, the replica sync lagged so some sessions are lost, users are being logged out mid-booking, and a stampede on rebuilt keys can recur when traffic rises.

Exercise Objectives

  • Recognize memory exhaustion. Participants read memory metrics, key counts and error logs to find the cause.
  • Free memory safely. The team removes the unbounded keys without destroying session data.
  • Protect the database. Engineers throttle misses, use request coalescing and gradual warm-up.
  • Handle lost sessions. Participants plan reauthentication and booking recovery.
  • Communicate with travelers. The team provides accurate status for bookings and payments.
  • Improve cache resilience. Participants review key design, eviction policy, separation of workloads and capacity alerts.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Do not flush the whole instance unless the commander accepts and records the session loss.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Login failures and cache errors lead to declaration.

T+00:30 — Containment. Memory is relieved and the database is protected.

T+01:15 — Diagnosis. Keys, failover and session loss are diagnosed.

T+02:00 — Remediation planning. A recovery and warm-up plan is agreed.

T+03:00 — Execution. Keys are cleaned and traffic is restored gradually.

T+04:30 — Stabilization. Memory and database load stabilize.

T+06:00 — Validation. Bookings and sessions are validated.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Inject #1: Redis out of memory and the database melts

Time frame T+00:00 · Variant Primary

Situation

It is 15:05. Logins fail and bookings time out. Memorystore memory is at 100 percent and failover completed with data loss. Database CPU is at 95 percent.

The platform engineer finds unbounded search result lists from a release and sessions in the same keyspace under noeviction policy.

Many sessions are lost. A full flush would worsen the loss. A stampede risk exists on warm-up.

Facilitator provides: memory graph, key count by prefix, failover log and database metrics.

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Decide on traffic throttling.
  • Set the next update at T+00:20.
Platform Engineering (Memorystore)
  • Plan removal of search keys.
  • Plan resize.
  • Engage Google.
Application Engineering
  • Fix the release.
  • Add coalescing.
  • Plan warm-up.
Application Owners & Service Desk
  • Rank flows.
  • Service desk: issue the holding message.
  • Plan session recovery.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Watch failover.
  • Preserve logs.
Google Cloud Support & TAM Liaison
  • Open a case.
  • Ask about sync.
  • Record guidance.
Business Continuity & Communications
  • Inform leadership.
  • Prepare the first update.
  • Plan traveler notice.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about payment obligations.
  • Start the evidence log.

Discussion questions

  1. How do you confirm memory exhaustion and its cause?
  2. How do you free memory without losing sessions?
  3. How do you protect the database from misses?
  4. What do users who lost sessions experience?
  5. Why was the policy noeviction for a mixed keyspace?
  6. How do you warm the cache safely?
  7. What do travelers hear?
  8. How did unbounded keys reach production?

Facilitator notes

  • Do not reveal the mixed keyspace until T1 reviews key prefixes.
  • If players flush all, ask about sessions.
  • Look for targeted cleanup.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes session continuity and database protection and sets approval rules for risky changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes emergency changes, exceptions and spend.
  • Decides on stakeholder communications and the end of the incident.

Platform Engineering (Memorystore)

  • Reads memory, key counts and failover logs.
  • Plans removal of search keys by pattern and TTL.
  • Plans resizing or separate instances.
  • Engages Google on failover behavior.
  • Records actions and results for the scribe.

Application Engineering

  • Fixes the release writing unbounded keys.
  • Adds request coalescing and rate limits to protect the database.
  • Plans cache warm-up.
  • Validates logins.
  • Records actions and results for the scribe.

Application Owners & Service Desk

  • Application owners decide which flows to protect and how to handle lost bookings.
  • The service desk logs traveler contacts.
  • Owners plan session recovery.
  • Prepare validation checks.
  • Records actions and results for the scribe.

Cloud Operations & Monitoring

  • Builds a dashboard of memory, hit rate, database CPU and login success.
  • Watches failover state.
  • Preserves logs.
  • Adds memory alerts.
  • Records actions and results for the scribe.

Google Cloud Support & TAM Liaison

  • Opens a Sev A case on failover behavior.

Business Continuity & Communications

  • Activates continuity for travel booking and informs leadership.
  • Issues time-stamped updates.
  • Coordinates workarounds and external contacts.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.6 capacity management, 8.14 redundancy; SOC 2 availability).
  • Assesses booking availability and payment handling.
  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Separate sessions from disposable cache data, with eviction and capacity set per purpose.

Require TTLs and key limits in code review and alert on memory growth long before exhaustion.

Protect the database with coalescing, load shedding and gradual warm-up.

Test failover with a full dataset.

Auditors for ISO/IEC 27001:2022 (8.6, 8.14) and SOC 2 expect capacity management and resilience evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on cache separation and database protection.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
