Hybrid DNS Forwarding Loop Between Local BIND and Azure Private DNS

Hybrid Cloud (Azure Focus)

Exercise Overview

This tabletop exercise examines a DNS forwarding loop in which on-premises BIND servers forward Azure zones to Azure DNS Private Resolver while Azure forwards on-premises zones back to BIND, so queries for unknown or newly created names circulate and saturate resolvers.

Participants are working-level: network and DNS engineers, cloud platform engineers, application owners, the service desk, security operations and monitoring staff, the Microsoft support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of conditional forwarders, private zones, resolver rulesets, recursion, caching and query amplification.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Alder Insurance uses BIND resolvers in two datacenters and an Azure DNS Private Resolver with inbound and outbound endpoints. A forwarding rule sends corp.alder.example to BIND. BIND forwards azure.alder.example to the inbound endpoint. A catch-all rule was added last week sending unmatched queries to BIND for logging.

At 08:30 on Monday, a new application deploys and queries names in a zone not yet delegated. The catch-all sends queries from Azure to BIND, BIND forwards unknown names to its default forwarder, which is the Azure inbound endpoint, and the loop begins. Query rates reach 400,000 per second. BIND CPU saturates, Azure resolver throttles and both sides return SERVFAIL or time out. Login, claims and email-related names fail to resolve intermittently.

What the team does not yet know: the loop is only triggered for names that do not match any rule, so many names work, negative caching masks some failures, rate limiting at the resolver would hide the problem but not fix it, and two security tools use the same resolvers for threat intelligence lookups.

Exercise Objectives

  • Recognize a forwarding loop. Participants read query logs and see the same names bouncing between resolvers.
  • Break the loop. The team removes the catch-all rule or the default forwarder in a controlled way.
  • Restore resolution. Engineers restore caches and verify critical names from both environments.
  • Protect security tooling. Participants check that security lookups still work.
  • Prevent recurrence in recovery. The team adds loop protections and rules review.
  • Improve DNS architecture. Participants review rule design, authority boundaries and monitoring.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Change one forwarding rule at a time and verify resolution from both sides after each change.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Intermittent resolution failures and resolver CPU alerts lead to declaration.

T+00:30 — Containment. The loop is confirmed and a rule is chosen to remove.

T+01:15 — Diagnosis. Rules and names affected are diagnosed.

T+02:00 — Remediation planning. A fix and verification plan is agreed.

T+03:00 — Execution. Rules are corrected in steps.

T+04:30 — Stabilization. Resolvers stabilize.

T+06:00 — Validation. Names are validated from both sides.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Resilience Architect Guidance

Define clear authority for each zone and avoid catch-all forwarding between environments.

Review forwarding changes jointly across on-premises and cloud teams and test names from both sides.

Add loop detection through query rate alerts and per-zone dashboards.

Keep security lookups on separate resolvers.

Auditors for ISO/IEC 27001:2022 (8.20, 8.32) and SOC 2 expect network configuration, change control and monitoring evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on DNS authority design and joint change review.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
