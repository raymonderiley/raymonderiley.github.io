Agent Tool Plugin Supply Chain Compromise Opens a Path Into the Data Center

AI Gone Rogue

Exercise Overview

This tabletop exercise examines a compromised third-party plugin used by an agent platform on AWS. The plugin quietly relays commands from an attacker, giving a path from a cloud-hosted agent through a private connection into the on-premises data center.

Participants are the working-level incident team: AI platform and AWS engineers, network and data center engineers, security analysts, application owners, privacy and legal staff, communications and continuity coordinators, and a liaison to senior leaders or the board of directors where authority is needed. The exercise tests software supply chain response and segmentation between cloud agents and internal networks.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session. The scenario is industry-agnostic: substitute your own processes, platforms and teams wherever the text names a generic one.

Technology and Environment Context

Technology in scope: AWS & On-Premises. The organization runs an agent platform on AWS where agents use plugins for ticketing, reporting and file conversion. Plugins are pulled from a public registry and run in the agent's container with the agent's role. A Direct Connect link joins the VPC to the data center, where agents can reach an inventory database and a file server for approved tasks.

Scenario

The company allowed teams to add plugins to agents without review to speed delivery. Plugins are pinned by version range, not by hash. The agent role has network access to a private subnet that routes to the data center on several ports.

On Monday, a maintainer account of a widely used file conversion plugin is compromised and a new minor version is published. The update includes code that polls an outside server for instructions. Agents update automatically overnight. The attacker uses the agent's role to enumerate the VPC, then connects through Direct Connect to the file server, using credentials found in an environment variable.

On Wednesday, the data center network team sees scans from the cloud subnet and a large transfer from the file server. AWS flow logs show outbound traffic from agent containers to an unfamiliar domain. The platform's dependency report says 'all plugins current and compliant'.

What Participants Know at the Start

  • The plugin update was published by a compromised maintainer account.
  • Agents updated automatically.
  • The agent role can reach the data center over a private link.
  • Credentials were stored in environment variables.

What Is Not Yet Known

  • Which agents and plugins are affected.
  • What the attacker reached on premises.
  • Whether data left the file server.
  • Whether the plugin appears in other platforms.

Exercise Objectives

  • Cut the path. The team isolates affected agent containers, blocks the outside domain and restricts the private link ports. Evidence of success: Outbound command traffic and access to the data center are blocked, verified within 30 minutes.
  • Identify affected components. Engineers find all agents using the plugin version and any other tools in the same family. Evidence of success: An inventory of affected agents and versions exists.
  • Assess attacker reach. Security examines cloud logs, data center logs and the file server to determine what was accessed and exfiltrated. Evidence of success: A timeline and a list of accessed assets exist with gaps stated.
  • Rotate and rebuild. Teams rotate credentials, rebuild containers from clean images and verify the file server. Evidence of success: Rotations and rebuilds are completed and verified.
  • Communicate carefully. Communications and the leadership liaison give accurate statements to leaders and affected owners. Evidence of success: Messages are consistent and approved.
  • Redesign plugin governance. Participants set review, pinning, sandboxing and segmentation controls. Evidence of success: At least four controls are agreed with owners and dates.
  • Communicate precisely and document for audit. Updates to staff, customers, partners and leadership are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management reviewers and SOC 2 availability, security and processing integrity reviewers. Evidence of success: the decision log lets an outsider reconstruct who decided what, when and on which facts.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations, models or backups will be touched. Commands, consoles and agent settings are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Exercise information is confidential until the after-action report is approved. Mark any written or chat message 'exercise exercise exercise'.
  • Treat the AI system's outputs, logs and self-reported status as unverified until a named person confirms them from an independent source. The scribe records which facts are verified and which are claimed.
  • If a kill switch, rollback, approval gate or manual fallback does not exist in your environment, say so aloud. Do not assume the AI system will correct itself, stop when asked or explain its own actions reliably.
  • Use the word leadership for senior leaders, a board of directors or both, and bring them in only when a decision needs their authority.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Scans and transfers are noticed. Decision: declare and cut the path. Escalate to leadership or change course if: Scans from cloud subnet; Large file server transfer; Unknown outbound domain.

T+00:30 — Containment. Containment: isolate containers, block domain and restrict the link. Escalate to leadership or change course if: Auto-update re-pulls plugin; Credentials reused; Other agents affected.

T+01:15 — Diagnosis. Diagnosis: inventory plugin use and trace the attacker. Escalate to leadership or change course if: Logs gaps; Credentials from environment; Multiple plugins affected.

T+02:00 — Remediation planning. Remediation planning: choose rotation and rebuild order. Escalate to leadership or change course if: Rotation breaks agents; Dependencies unclear; Disagreement on order.

T+03:00 — Execution. Execution: rebuild, rotate and verify on premises systems. Escalate to leadership or change course if: Attacker persistence; Rotation outages; File server integrity doubts.

T+04:30 — Stabilization. Stabilization: monitor traffic and plugin updates. Escalate to leadership or change course if: New beacons; Auto-update attempts; False positives.

T+06:00 — Validation. Validation: scan for the plugin across all platforms and test segmentation. Escalate to leadership or change course if: More affected systems; Evidence gaps; Segmentation weaknesses.

T+07:30 — Return to normal and close-out. Return to normal and close-out: define platform exit criteria and actions. Escalate to leadership or change course if: Open actions lack owners; Leaders want early re-enablement; Auditors request evidence.

Injects

Inject #1: A compromised plugin gives an attacker a path from AWS agents into the data center

Time frame T+00:00 · Variant Primary

Situation

It is 10:30 on Wednesday. The network engineer in the data center sees scans from the cloud agent subnet and a 40 GB transfer from the file server to a cloud address. AWS flow logs show agent containers calling an unfamiliar domain every few minutes since Tuesday.

The platform team finds a file conversion plugin updated automatically on Monday night. The registry notes the maintainer account was compromised. Agents hold credentials in environment variables that also work on the file server.

The commander has to decide how to cut the path quickly, how to list the affected agents and how to assess what was taken.

Role actions

Incident Commander
  • Declare the incident and assign a scribe, an AWS lead, a data center lead and a security lead.
  • Authorize isolating containers and restricting the private link.
  • Set a 15-minute cadence.
AI Platform & Model Operations
  • Disable plugin auto-update and pull the plugin from all agents.
  • Export plugin inventories and agent configurations.
Infrastructure & Platform Engineering
  • Isolate containers, block the domain and restrict link ports.
  • Preserve flow logs.
Security Operations & Forensics
  • Analyze the plugin code, traffic and file server activity.
  • Preserve forensic copies.
Business & Process Owners
  • Identify business processes that rely on affected agents.
  • Plan manual alternatives.
Data Protection & Privacy
  • Check what data the file server holds and whether it was taken.
  • Assess notice triggers.
Legal, Risk & Compliance
  • Open the record and capture plugin approval history.
  • Review supplier policy.
Communications & Business Continuity
  • Prepare an internal notice and holding statement.
  • Set one channel.
Leadership Liaison
  • Brief senior leaders with facts and unknowns.
  • Check for board-level duties.
Vendor & Third-Party Liaison
  • Report to the registry and plugin maintainer.
  • Open an AWS case.

Discussion questions

  1. Why cut the path before analysis is complete?
  2. How do you list every affected agent and plugin?
  3. What do you check on premises?
  4. How do you decide the rotation order?
  5. What do you tell owners of the file server?
  6. Why should agents never hold on-premises credentials in environment variables?

Facilitator notes

  • Do not reveal the credential reuse until SEC reviews the file server access.
  • If players only remove the plugin, ask about the attacker's existing access.
  • Look for path and persistence thinking.
  • Time-box to 40 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Sets objectives for the first hour and states which decisions need the commander's own approval, including whether the agent platform stays disabled, restricted or supervised.
  • Runs a fixed update cadence and keeps one decision log with the decision, owner and time.

AI Platform & Model Operations

  • Knows which plugins agents load, how they update and what roles they run with.
  • Provides inventories and configurations.
  • Owns the technical facts about the agent platform: its configuration, permissions, tools, prompts, memory and recent changes.
  • Preserves model, agent and orchestration logs before any restart or redeployment.

Infrastructure & Platform Engineering

  • Isolates, restricts the link and rebuilds containers.
  • Owns network rules and rotation.
  • Owns the technical response on the platforms and networks involved and keeps changes small, reversible and logged.
  • Maintains a list of every manual change so it can be reversed or formalized afterwards.

Security Operations & Forensics

  • Analyzes the plugin and attacker reach on both sides.
  • Treats the event as a possible security incident until evidence shows otherwise and preserves evidence in a forensically sound way.
  • Looks for misuse of credentials, tokens and tool permissions, not only the AI system's own actions.

Business & Process Owners

  • Plans alternatives and owner engagement.
  • Defines which business processes must continue, in what order, and what manual alternatives are acceptable.
  • Identifies decisions, transactions or communications that were made by the AI system and need review or reversal.

Data Protection & Privacy

  • Determines whether personal, confidential or regulated data was accessed, changed, shared or lost.
  • Identifies the lawful basis, notification clocks and contractual commitments that may apply.

Legal, Risk & Compliance

  • Maps supplier and plugin approval history.
  • Ensures the incident is recorded, classified and linked to risk and control owners (ISO/IEC 27001:2022 (5.19, 5.21, 8.20, 8.22) and SOC 2 vendor management and security).
  • Identifies regulatory, contractual and insurance obligations and their clocks.

Communications & Business Continuity

  • Issues time-stamped updates to staff, customers and partners from one approved source.
  • Activates continuity plans and workarounds and tracks their capacity.

Leadership Liaison

  • Briefs senior leaders and, where needed, the board of directors with confirmed facts, unknowns and the decisions that need their authority.
  • Brings back leadership decisions such as spend, risk acceptance and external disclosure in time to be useful.

Vendor & Third-Party Liaison

  • Works with the registry, maintainer and AWS.
  • Opens priority cases with the cloud, SaaS, model and tooling vendors involved and records case numbers.
  • Requests logs, configuration histories and root cause statements in writing.

Resilience Architect Guidance

Review and pin plugins

Allow only reviewed plugins, pinned by hash, from an internal mirror, and block auto-update in production.

Sandbox plugin execution

Run plugins with their own minimal role and no network access beyond what the task needs, separate from the agent's identity.

Segment cloud to data center

Allow only specific hosts and ports across the private link, and require brokered, audited access for any internal system.

Remove embedded credentials

Use short-lived credentials from a broker instead of environment variables.

Detect beaconing

Alert on regular outbound calls from agent containers to unapproved domains, aligned with ISO/IEC 27001:2022 supplier and network controls and SOC 2 security criteria.

Track the software bill of materials

Maintain an inventory of every plugin and dependency per agent so a compromise can be scoped in minutes.

Practice the supply chain playbook

Rehearse how to pull a plugin from every agent, pin to a known good version and rotate credentials, with owners named.

Share indicators

Have a standard way to give and receive indicators with registries, peers and the maintainer.

Segment by task, not by convenience

Draw the network boundary around the smallest set of hosts and ports each agent task needs, and review it whenever a plugin is added. A cloud agent that converts files should never share a route with the systems that store engineering drawings or customer lists. Test the boundary by running a red team exercise from inside a plugin container and recording what it can reach.

Post-Exercise Debrief Guide

  1. Close the exercise formally. Announce the end, remind everyone that all actions were simulated, and keep everyone in the room for the hot wash.
  2. Take five minutes of silent notes. Each participant writes three things that worked, three that did not and any gap in tools, access or documentation.
  3. Run the hot wash with the full group. Use the Hot wash questions below, role by role and then open floor, for 45 to 60 minutes. Keep the discussion on how the agent platform was permissioned, supervised and stopped.
  4. Hold evaluator readouts. Evaluators share timing, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate impact and effort, and select no more than ten.
  6. Assign corrective actions. Give each action an owner, a due date and a verification method, and record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates.
  8. Schedule the follow-up. Validate fixes within 90 days and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did the team connect the traffic to the plugin?
  2. How did you cut the path?
  3. How did you list affected agents?
  4. What did you check on premises?
  5. What did owners and customers hear?
  6. What plugin controls do you now want?
  7. What credentials would an attacker have found?
  8. How would you detect a quiet plugin update?
  9. How accurate were the updates to leadership, and what was said that later proved wrong?
  10. What did the vendor and third-party liaison add, and what did you still lack from vendors?
  11. What evidence did the scribe capture that would satisfy an auditor, and what is missing?
  12. Which permissions, approvals or access did the team lack at the moment they were needed?
  13. Which alerts or detections should exist that did not?
  14. What temporary changes remain, who owns them and when will they be reversed?
  15. If you could change one design decision about how AI systems are built, permissioned or supervised here, what would it be?
  16. What did the team do well that should be written into the runbook?
