Insider Threat Weaponizing Automated Code Generation to Implant Logic Bombs

AI Failure & Autonomous Agent Disruption

Exercise Overview

This tabletop exercise examines an insider using an AI code generation assistant to produce large volumes of plausible code that hides logic bombs in payment and data retention services, evading review through volume and consistent style.

Participants are working-level: software security engineers, application platform engineers, application owners, the service desk, security operations analysts, the AI platform and cloud support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of code review limits, provenance, release control, rollback and insider response.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Alder Payments lets developers use an approved AI coding assistant. Pull requests above a size threshold receive a lighter automated review. A senior developer in the platform team has broad merge rights. Releases run weekly with automated deployment after tests pass.

At 10:00 on Thursday, a routine audit finds a function in the settlement service that checks the system date and, on the first of next month, changes a rounding rule and deletes transaction audit rows older than 90 days. It appears in four services committed over six weeks within large AI-assisted pull requests. The developer resigned last week and has access until Friday.

What the team does not yet know: whether other logic bombs exist, whether any have already shipped, whether the developer's accounts have been used since resignation, and how many services share the code.

Exercise Objectives

  • Recognize hidden malicious logic. Participants identify the logic bomb and its trigger.
  • Contain the insider. The team restricts the developer's access and preserves evidence.
  • Find all malicious code. Engineers sweep repositories for related patterns.
  • Block deployment. Participants halt releases and verify production state.
  • Remediate safely. The team removes the code and validates behavior.
  • Improve code integrity. Participants review review limits, provenance and release controls.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Restrict the developer's access and preserve repositories and logs before removing any code, and freeze releases until a sweep is complete.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. A discovered logic bomb leads to declaration.

T+00:30 — Containment. Access is restricted and releases frozen.

T+01:15 — Diagnosis. Scope and shipped code are diagnosed.

T+02:00 — Remediation planning. A remediation plan is agreed.

T+03:00 — Execution. Code is removed and verified.

T+04:30 — Stabilization. Releases resume with controls.

T+06:00 — Validation. Production is validated.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes code that can be traced to a reviewed intent and sets approval rules for risky changes.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes emergency changes, exceptions and spend.
  • Decides on stakeholder communications and the end of the incident.

Software Security Engineering

  • Restricts the developer's access and reviews commits.
  • Freezes releases.
  • Plans a code sweep.

  • Records actions and results for the scribe.

Application Platform Engineering

  • Checks production deployments for the code.

  • Coordinates workarounds and external contacts.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 8.4 access to source code, 8.25 secure development lifecycle, 8.28 secure coding, 8.32 change management, 6.5 responsibilities after termination; SOC 2 security and change management).
  • Assesses secure development and change control.
  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Limit pull request size or apply stronger review to large AI-assisted changes and require two reviewers for sensitive services.

Tag and track AI-generated code and its prompts where possible.

Restrict merge rights and enforce separation between authors and approvers.

Scan for date-triggered, destructive and obfuscated logic.

Auditors for ISO/IEC 27001:2022 (8.4, 8.25, 8.28, 8.32) and SOC 2 expect secure development and change control evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on preserve-first and release control.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How did you confirm the logic?
  2. What did you do with access?
  3. How did you sweep?
  4. How did you handle releases?
  5. What review changes do you want?
  6. What provenance do you need?
  7. How accurate were updates to leadership?
  8. What did the AI Platform Vendor & Cloud Support Liaison add?
  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
