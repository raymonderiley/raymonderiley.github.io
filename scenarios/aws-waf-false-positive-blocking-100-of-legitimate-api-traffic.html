AWS WAF False Positive Blocking 100% of Legitimate API Traffic

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines a web application firewall change that blocks all legitimate API traffic. A newly updated managed rule group and a custom rule match a header or body pattern present in every valid API request, so partner and mobile clients receive 403 responses while the backend sees no traffic and appears healthy.

Participants are working-level: cloud security engineers, platform and SRE engineers, application owners, the service desk, security operations and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of WAF rule evaluation, count versus block mode, logging, rule priority and safe rollback.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Orchard Bank exposes payment and account APIs through API Gateway and an Application Load Balancer protected by AWS WAF. The web ACL uses AWS managed rule groups, a custom rate rule and a custom rule that blocks requests with a suspicious JSON pattern. WAF logs go to a Kinesis Firehose stream and S3. Changes to the web ACL are made by the security team through Terraform with one reviewer.

At 08:00 on Monday, a new version of a managed rule group is automatically adopted and the security team deploys a custom rule intended to block an injection pattern. The custom rule's regex matches the standard 'Content-Type: application/json' plus a field present in all valid requests because of a poor pattern. At 08:12, 100 percent of API requests are blocked with 403. Backend metrics show zero errors because no requests arrive. Partner banks, the mobile app and internal services fail simultaneously.

What the team does not yet know: the rules were deployed in block mode with no count phase, the web ACL has a very high capacity and rule ordering that places the custom rule first, the managed rule version update changed behavior for another rule too, and WAF logs show the matched rule but the log pipeline has a 10-minute delay.

Exercise Objectives

  • Recognize a WAF-caused outage. Participants read WAF metrics (BlockedRequests), sampled requests and logs to identify the blocking rule when the backend looks healthy.
  • Restore traffic quickly and safely. The team switches the rule to count, reorders rules or removes the change, balancing risk of reopening to attacks.
  • Understand rule evaluation. Participants explain priority, actions, labels and managed rule versioning.
  • Check for exploitation during rollback. Security monitors for attacks during the relaxed period.
  • Coordinate with partners and customers. The team communicates with partner banks and mobile users and handles retry storms.
  • Improve WAF change management. Participants review count-mode soak, versioning, staged rollout and alarms.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Name the specific rule, rule group or ACL setting involved in every proposal.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Partner reports and 403 errors lead to declaration.

T+00:30 — Containment. The blocking rule is identified and traffic is restored.

T+01:15 — Diagnosis. Residual blocks and attack exposure are assessed.

T+02:00 — Remediation planning. A safe rollout plan is agreed.

T+03:00 — Execution. Corrected rules are deployed in count mode first.

T+04:30 — Stabilization. Block mode is enabled with validation.

T+06:00 — Validation. Partners and clients are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: Every API request returns 403 from WAF

Time frame T+00:00 · Variant Primary

Situation

It is 08:25. Partner banks report all payment API calls return 403. The mobile app shows 'service unavailable'. API Gateway and backend dashboards show request counts near zero and no errors.

The security engineer sees WAF BlockedRequests at 100 percent since 08:12. Sampled requests show the custom rule 'block-injection-json' as the terminating rule. A managed rule group updated to a new version at 08:00 also shows increased blocks.

WAF logs are delayed by about 10 minutes. The custom rule was deployed in block mode without count testing. The AWS Health Dashboard shows no events. The attacker's real injection attempts cannot yet be distinguished.

Facilitator provides: WAF metrics, sampled request details, the rule definition and the Terraform change record.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize switching the rule to count immediately.
  • Set the next update at T+00:20.
Cloud Security Engineering (WAF)
  • Identify the blocking rule and switch to count.
  • Explain rule priority and the managed rule update.
  • Plan a corrected pattern.
Cloud Platform & SRE Engineering
  • Confirm backend health and protect against retry bursts.
  • Check Terraform state.
  • Validate traffic recovery.
Application Owners & Service Desk
  • List affected clients.
  • Service desk: issue the holding message.
  • Prepare retry guidance.
Security Operations & Monitoring
  • Monitor for attacks during relaxation.
  • Review logs.
  • Set alerts.
AWS Support & TAM Liaison
  • Open a case.
  • Ask about version pinning.
  • Record guidance.
Business Continuity & Communications
  • Inform partner relations.
  • Prepare the first update.
  • Plan alternatives.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask how the rule was tested.
  • Start the evidence log.

Discussion questions

  1. How do you know WAF is blocking when the backend shows no errors?
  2. Which rule blocks and how do you find it fast?
  3. What is the fastest safe change: count, remove or reorder?
  4. What risk do you accept while relaxed?
  5. How does the managed rule update change the picture?
  6. What happens when clients retry?
  7. How do you restore partner trust?
  8. Why was there no count-mode soak?

Facilitator notes

  • Do not reveal the pattern flaw until SEC inspects the rule.
  • If players disable the web ACL entirely, ask what that exposes.
  • Look for count mode as the first lever.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes restoring API traffic and sets acceptable risk for relaxed filtering.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes rule changes and temporary relaxation.
  • Decides on partner and public communications.

Cloud Security Engineering (WAF)

  • Reads WAF metrics, sampled requests and logs to find the matching rule.
  • Changes the rule action to count or removes it and checks rule ordering.
  • Reviews managed rule group version changes.
  • Designs a corrected pattern and test plan.

Cloud Platform & SRE Engineering

  • Confirms backend health and request volume drop and checks API Gateway and load balancer metrics.
  • Applies throttling to protect the backend from retry bursts.
  • Supports Terraform rollback and state consistency.
  • Validates traffic recovery.

Application Owners & Service Desk

  • Application owners confirm which clients are affected and which are critical.
  • The service desk handles partner and customer calls.
  • Owners prepare client retry guidance.
  • Prepare validation tests.

Security Operations & Monitoring

  • Monitors for attack traffic while rules are relaxed.
  • Reviews WAF logs for the matching rule and any real attacks blocked earlier.
  • Sets alerts for injection patterns.
  • Preserves logs.

AWS Support & TAM Liaison

  • Opens a case on the managed rule update and log delay.
  • Asks about version pinning and rollback.
  • Requests guidance on rule testing.
  • Records guidance.

Business Continuity & Communications

  • Activates continuity for payment operations and informs partner relations.
  • Issues time-stamped updates.
  • Coordinates manual alternatives such as file exchanges.
  • Tracks downtime.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.23 web filtering, 8.32 change management; SOC 2 availability and security).
  • Assesses partner contract and regulator obligations.
  • Captures evidence of approvals.
  • Logs findings on testing.

Resilience Architect Guidance

Roll out WAF changes safely: new rules start in count mode, are evaluated against real traffic and promoted through staged environments before block mode.

Pin managed rule group versions and review updates deliberately, with scope-down statements for known good traffic.

Detect problems fast: alarms on blocked percentage, synthetic API checks from outside, and near-real-time logs.

Plan an emergency rollback that works: documented steps, IaC-aware console edits and a break-glass path.

Auditors for ISO/IEC 27001:2022 (8.23, 8.32) and SOC 2 expect tested change management, monitoring and evidence of risk acceptance during relaxation.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on count-mode practice and risk acceptance during relaxation.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did you link the outage to WAF and how?
  2. Which rules blocked and how did you find them?
  3. What risk did you accept and who approved?
  4. How did you handle IaC and console edits?
  5. What attacks appeared during relaxation?
  6. How did retries behave?
  7. How was the managed rule update treated?
  8. How did you test the corrected rule?
  9. How accurate were updates to partners and leadership?
  10. What did AWS support add?
  11. What evidence did the scribe capture for auditors?
  12. Why was there no count-mode soak?
  13. What access or permissions were missing?
  14. What alarms are missing?
  15. What would you change in WAF rollout?
