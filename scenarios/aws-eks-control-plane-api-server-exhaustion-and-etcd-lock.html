AWS EKS Control Plane API Server Exhaustion and Etcd Lock

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines an EKS control plane that becomes unresponsive because a misbehaving controller floods the Kubernetes API server with list and watch requests, driving request latency up and etcd toward its storage limit. kubectl hangs, deployments stall, autoscaling stops and nodes cannot report status.

Participants are working-level: Kubernetes platform engineers, application and operator engineers, application owners, the service desk, cloud operations and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of what AWS manages in EKS, what customers control, and how data plane workloads behave when the control plane is impaired.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Brightwater Retail runs its storefront on an EKS cluster with 180 nodes across three Availability Zones, using Karpenter for node scaling and several custom operators. API server audit logs and control plane logging are enabled for 'api' and 'audit' to CloudWatch Logs.

At 13:00 on Saturday, a new version of an inventory operator is released with a bug that re-lists all Pods and ConfigMaps every second without caching and creates a custom resource for each reconcile. Within 30 minutes, API server request latency rises from 40 ms to 12 seconds. etcd database size grows from 2 GB toward the 8 GB limit because of millions of leftover custom resource objects. By 13:50, kubectl times out, HPA and Karpenter cannot update, new Pods are not scheduled, and nodes show NotReady due to delayed heartbeats.

What the team does not yet know: running Pods continue to serve traffic as long as nodes keep running, but any node replacement or Pod restart will not succeed, the API server priority and fairness settings were never tuned, cleanup of custom resources requires API access that is itself overloaded, and the operator's service account has cluster-wide list permissions.

Exercise Objectives

  • Separate control plane from data plane impact. Participants distinguish what still works (running Pods and ALB traffic) from what stops (scheduling, scaling, deploys).
  • Find the offending client. The team uses API server audit logs, request metrics and APF metrics to identify the high-volume user agent and service account.
  • Reduce load safely. Engineers scale down the operator, revoke its access or apply flow control, without making recovery impossible.
  • Handle etcd growth. Participants plan deletion of leftover resources, avoid destructive actions and work with AWS on the managed etcd.
  • Protect running workloads. The team freezes changes and avoids node churn while the control plane is degraded.
  • Improve cluster governance. Participants review operator testing, rate limits, quotas on objects and monitoring.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Be explicit about which actions require the Kubernetes API and which do not; a plan that assumes kubectl works is incomplete.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Hung kubectl, stalled deployments and NotReady nodes lead to declaration.

T+00:30 — Containment. Changes are frozen and the likely source of API load is identified.

T+01:15 — Diagnosis. Audit logs confirm the operator and the etcd growth.

T+02:00 — Remediation planning. A plan to cut load and clean up objects is made with AWS.

T+03:00 — Execution. The operator is stopped and flow control is applied.

T+04:30 — Stabilization. The API recovers and nodes return to Ready.

T+06:00 — Validation. Workloads, scaling and scheduling are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: API server latency spikes and nodes go NotReady

Time frame T+00:00 · Variant Primary

Situation

It is 14:05. Engineers report kubectl commands time out. The storefront is still serving most traffic but cart pods that crashed are not being replaced, and the HPA has stopped scaling ahead of the weekend sale. Several nodes appear NotReady.

The platform engineer sees control plane metrics: apiserver request latency p99 at 12 seconds, inflight requests at the limit and etcd database size at 7.1 GB. CloudWatch Logs Insights over the audit log shows 64 percent of requests from one user agent, the inventory operator service account, issuing LIST calls every second.

The operator team confirms a release 65 minutes ago. The AWS Health Dashboard shows no EKS events. Karpenter cannot provision nodes. A sale event begins in three hours.

Facilitator provides: the latency graphs, the audit log summary, the etcd size trend and the operator release notes.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Authorize a freeze on deployments and node changes.
  • Set the next update at T+00:20.
Kubernetes Platform Engineering (EKS)
  • Identify the offending client and explain how.
  • Plan to stop the operator without needing a working API.
  • Describe what still works and what does not.
Application & Operator Engineering
  • Confirm the release and loop bug.
  • Prepare a rollback.
  • Estimate leftover custom resources.
Application Owners & Service Desk
  • Confirm which workloads must not restart.
  • Service desk: issue the holding message.
  • Plan sale limits.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Confirm log delivery.
  • List missing alarms.
AWS Support & TAM Liaison
  • Open a case.
  • Ask about etcd limits.
  • Record guidance.
Business Continuity & Communications
  • Inform merchandising.
  • Prepare the first update.
  • Ask for documented RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask how the operator was tested.
  • Start the evidence log.

Discussion questions

  1. How do you tell API server exhaustion from node or network problems?
  2. How do you find the offending client?
  3. How do you stop the operator when kubectl is unresponsive?
  4. What happens to running Pods and why?
  5. How do you deal with etcd growth you cannot reach with kubectl?
  6. Should you replace nodes or not?
  7. What is the plan for the sale event?
  8. What do you tell merchandising and leadership?

Facilitator notes

  • Do not reveal the etcd size until the platform engineer checks metrics.
  • If players restart nodes, ask what happens when they cannot rejoin.
  • Look for IAM or scaling-based ways to stop the operator.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes keeping existing storefront Pods serving and decides on a change freeze.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes stopping the operator or revoking its access.
  • Decides on a traffic cap for the sale event.

Kubernetes Platform Engineering (EKS)

  • Checks EKS control plane metrics and API server logs, request latency and APF queues.
  • Identifies the high-volume user agent from audit logs in CloudWatch Logs Insights.
  • Plans stopping the operator through paths not needing the overloaded API, such as scaling via the AWS console or IAM revocation.
  • Plans staged cleanup of custom resources with throttled deletes.

Application & Operator Engineering

  • Identifies the operator release and the loop bug.
  • Prepares a fix or rollback and reviews caching and watch usage.
  • Estimates how many custom resources exist.
  • Prepares a safe deletion script with limits.

Application Owners & Service Desk

  • Application owners confirm storefront health and which workloads cannot restart.
  • The service desk logs customer reports and issues guidance.
  • Owners decide on sale event limits.
  • Prepare validation tests.

Cloud Operations & Monitoring

  • Builds a dashboard of API latency, request rate by client, etcd size and Ready nodes.
  • Confirms control plane log delivery.
  • Checks AWS Health.
  • Adds alarms on API latency and etcd size.

AWS Support & TAM Liaison

  • Opens a high-severity case with cluster ID, timelines and the offending client.
  • Asks about etcd size limits and managed recovery options.
  • Requests help throttling or isolating the client.
  • Records guidance.

Business Continuity & Communications

  • Activates continuity for the sale event and informs merchandising.
  • Issues time-stamped updates.
  • Coordinates customer messaging.
  • Tracks downtime.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.6 capacity management, 8.32 change management; SOC 2 availability).
  • Assesses commercial exposure.
  • Captures evidence of release controls.
  • Logs findings on operator governance.

Resilience Architect Guidance

Know the shared responsibility line. AWS manages the EKS control plane, but customers control the clients that load it. Treat operators and controllers as production software with load tests, informers and caching, and rate limits.

Tune the API server's protection: API Priority and Fairness, resource quotas on object counts, and least-privilege RBAC so a single service account cannot list the whole cluster every second.

Monitor the control plane: API latency, inflight requests, etcd size and audit log patterns, with alarms and a runbook that does not depend on kubectl.

Design for control plane loss: critical workloads must keep serving without scheduling, with static capacity buffers before big events and node credential lifetimes understood.

Auditors for ISO/IEC 27001:2022 (8.6, 8.32) and SOC 2 expect capacity monitoring, change testing evidence and tested runbooks.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on stopping the offending client without kubectl.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did you identify the offending client and how?
  2. What did you assume still worked and was it true?
  3. How did you stop the operator without the API?
  4. How did the team handle etcd growth and AWS's role?
  5. What happened to nodes and Pods?
  6. How did you decide about the sale event?
  7. How were deletions controlled?
  8. What happened when the API recovered?
  9. How accurate were messages to leadership?
  10. What did AWS support add?
  11. What evidence did the scribe capture for auditors?
  12. How are operators tested before release?
  13. What access or permissions were missing?
  14. What alarms would have warned you earlier?
  15. What would you change in cluster governance?
