GCP Cloud KMS Cloud HSM Cryptographic Key Revocation

Google Cloud Resiliency

Exercise Overview

This tabletop exercise examines the disabling and scheduled destruction of Cloud HSM-backed customer-managed encryption keys by a compromised or mistaken administrator, which renders encrypted databases, storage and backups unreadable and starts a countdown to irreversible loss.

Participants are working-level: cryptography and key management engineers, application and data engineers, data owners, the service desk, security operations and monitoring staff, the Google Cloud support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of key versions, scheduled destruction, key rings, IAM on keys, CMEK dependencies and key recovery.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Hawthorne Insurance uses customer-managed encryption keys in Cloud HSM for BigQuery datasets, Cloud Storage buckets, Cloud SQL instances and backups. Keys are in four key rings with a default 24-hour destruction schedule for versions. Two administrators hold key admin roles and the group is large.

At 01:45 on Saturday, a privileged account disables the primary key versions for the claims database and schedules their destruction. Cloud SQL and BigQuery operations begin failing. Backups encrypted with the same keys cannot be restored. Security alerts fire at 02:10 and the account owner states they did not make the change. The scheduled destruction occurs in 24 hours.

What the team does not yet know: restoring a key version scheduled for destruction is possible within the window, the account may be compromised, other keys have been touched, and some old backups use a key version that was destroyed last month for a legitimate rotation.

Exercise Objectives

  • Recognize key revocation. Participants read audit logs and error messages to link failures to disabled keys.
  • Restore the keys safely. The team restores scheduled-for-destruction versions and re-enables keys under dual control.
  • Contain the privileged account. Engineers revoke access, preserve evidence and check other keys.
  • Protect data availability. Participants prioritize recovery of claims data and backups.
  • Treat it as a possible attack. The team coordinates with security operations and avoids actions that destroy evidence.
  • Improve key governance. Participants review destruction schedules, role separation, alerts and key recovery runbooks.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Key actions require two approvers and are logged; never destroy or export key material during the incident.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Failing databases and key alerts lead to declaration.

T+00:30 — Containment. Keys are restored and the account contained.

T+01:15 — Diagnosis. Key state and scope are diagnosed.

T+02:00 — Remediation planning. A recovery and hardening plan is agreed.

T+03:00 — Execution. Keys and services are restored in order.

T+04:30 — Stabilization. Services and backups stabilize.

T+06:00 — Validation. Integrity and security posture are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Discussion questions

  1. How do you confirm key revocation is the cause?
  2. What is the safest first action?
  3. How does dual control work during an incident?

  • Decides on stakeholder communications and the end of the incident.

  • Captures evidence of decisions and approvals.
  • Logs findings for the debrief.

Resilience Architect Guidance

Use long destruction windows, small key admin groups, dual control and alerts on key state changes.

Test backup restore with current key versions regularly and track key versions needed by each backup.

Separate key admin from data admin duties.

Protect privileged accounts with strong authentication and just-in-time access.

Auditors for ISO/IEC 27001:2022 (8.24, 8.2, 8.13) and SOC 2 expect key management, privileged access and backup restore evidence.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on key destruction safeguards and backup restorability.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

  1. How did you link failures to the keys?
  2. How did you restore keys?
  3. How did you apply dual control?
  4. How did you contain the account?
  5. How did you handle the old backup issue?
  6. How did you prioritize claims?
  7. How accurate were updates to leadership?
  8. What did the Google Cloud Support & TAM Liaison add?
  9. What evidence did the scribe capture for auditors?
  10. What access or permissions were missing?
  11. What alerts are missing?
  12. What temporary changes remain and who owns them?
  13. What would you change in the design?
  14. What did the team do well?
  15. What surprised you?
