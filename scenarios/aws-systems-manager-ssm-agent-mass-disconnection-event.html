AWS Systems Manager (SSM) Agent Mass Disconnection Event

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines the simultaneous loss of Systems Manager connectivity for thousands of managed instances. A change to VPC endpoints, a proxy configuration or an IAM role causes SSM agents to report 'ConnectionLost'. Patching, Session Manager access, Run Command, inventory and automation all stop, and operators discover that they have lost their main path into servers.

Participants are working-level: cloud operations and systems management engineers, platform and SRE engineers, application owners, the service desk, cloud security and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of SSM agent connectivity, VPC endpoints, instance profiles, break-glass access and the risk of mass remediation.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Redstone Insurance manages 4,800 EC2 instances in 26 accounts with Systems Manager. Instances sit in private subnets without public IP addresses and reach SSM, EC2 Messages and SSM Messages through interface VPC endpoints. SSH and RDP are closed by policy; Session Manager is the approved access method. A monthly patch window begins at 22:00 Saturday.

At 21:40 Saturday, a network engineer applies a Terraform change that replaces shared VPC endpoint security groups in the central networking account to reduce rules. The new security group omits TCP 443 ingress from several workload CIDRs. Within minutes, agents cannot reach the endpoints. By 21:55, 3,900 instances show 'ConnectionLost' in Fleet Manager, and a patch baseline Run Command begun at 21:50 stalls with partial effects.

What the team does not yet know: about 600 instances were mid-patch and some rebooted into a half-patched state, a legacy application team has an emergency SSH key path that bypasses policy, several production database servers have no other access, and agents will retry with exponential backoff so recovery may be slow even after the fix.

Exercise Objectives

  • Recognize and scope an SSM outage. Participants use Fleet Manager, CloudWatch and VPC flow logs to understand which instances, accounts and endpoints are affected.
  • Restore connectivity safely. The team reverts or corrects the security group and checks DNS, endpoint policies and instance profiles.
  • Control in-flight patching. Engineers halt patch runs, identify half-patched servers and avoid mass reboots.
  • Maintain emergency access. Participants decide on break-glass access paths for critical servers without violating policy.
  • Check for security implications. The team assesses whether the loss of SSM left monitoring or response gaps.
  • Improve resilience and governance. Participants review endpoint redundancy, change control, patch window safeguards and alternatives.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • Be explicit about which instances or accounts you mean; do not propose fleet-wide commands without stating the blast radius.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. ConnectionLost alarms and failed patch runs lead to declaration.

T+00:30 — Containment. Patching is halted and the network change is identified.

T+01:15 — Diagnosis. Scope and half-patched servers are identified.

T+02:00 — Remediation planning. A restore and validation plan is agreed.

T+03:00 — Execution. Connectivity is restored in stages.

T+04:30 — Stabilization. Agents reconnect and health is verified.

T+06:00 — Validation. Patch state and compliance are verified.

T+07:30 — Return to normal and close-out. Normal operations resume and the incident is closed for debrief.

Injects

Inject #1: 3,900 instances lose Systems Manager connectivity during patching

Time frame T+00:00 · Variant Primary

Situation

It is 22:05. Fleet Manager shows 3,900 of 4,800 instances in 'ConnectionLost'. The patch window Run Command stalled with 'In Progress' on 600 instances. Operators cannot open Session Manager to any affected server.

The SRE finds that the VPC endpoint security group was replaced at 21:40 in the central networking account and no longer allows 443 from several workload CIDRs. DNS for endpoints resolves correctly.

Some instances rebooted mid-patch. A legacy application team mentions an SSH key path that exists outside policy. The AWS Health Dashboard shows no events. Business teams expect systems to be patched by Sunday 06:00.

Facilitator provides: Fleet Manager counts, the Terraform change diff, the patch run status and the production server list.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Freeze changes and halt the patch window.
  • Set the next update at T+00:20.
Cloud Operations & Systems Management Engineering
  • Stop in-flight patch runs.
  • Identify half-patched instances.
  • Plan staged recovery.
Cloud Platform & SRE Engineering
  • Revert or correct the security group.
  • Verify endpoints and DNS.
  • Prepare approved break-glass access.
Application Owners & Service Desk
  • Identify servers at risk.
  • Service desk: issue the holding message.
  • Prepare application checks.
Cloud Security & Monitoring
  • Assess monitoring gaps.
  • Check the SSH bypass.
  • Preserve logs.
AWS Support & TAM Liaison
  • Open a case.
  • Ask about reconnection.
  • Record guidance.
Business Continuity & Communications
  • Inform business owners.
  • Prepare the first update.
  • Ask about patch deadlines.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask how the change was reviewed.
  • Start the evidence log.

Discussion questions

  1. How do you tell an endpoint connectivity failure from an IAM or agent failure?
  2. What do you do about the in-flight patch run?
  3. How do you find half-patched servers?
  4. What break-glass access is appropriate and who approves it?
  5. How do you restore connectivity without a stampede or further disruption?
  6. Do you use the legacy SSH path?
  7. What did the loss of SSM mean for security monitoring?
  8. What do business owners need to hear?

Facilitator notes

  • Do not reveal the half-patched servers until SSM reviews run output.
  • If players run a fleet-wide command to fix agents, ask about blast radius.
  • Look for stopping the patch run as the first move.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes production database and claims servers and sets the change freeze.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes break-glass access and any emergency rollback.
  • Decides on postponing the patch window.

Cloud Operations & Systems Management Engineering

  • Reads Fleet Manager status, patch run output and SSM agent logs.
  • Stops in-flight Run Command and State Manager associations.
  • Plans staged reconnection checks and rerun of patching.
  • Identifies half-patched instances.

Cloud Platform & SRE Engineering

  • Reviews VPC endpoint and security group changes and plans the correction or revert.
  • Verifies DNS and routing for endpoints.
  • Prepares break-glass access via EC2 Instance Connect Endpoint or serial console where approved.
  • Monitors application health.

Application Owners & Service Desk

  • Application owners identify servers at risk and any mid-patch effects.
  • The service desk handles reports of access failures.
  • Owners prepare application checks.
  • Prepare validation tests.

Cloud Security & Monitoring

  • Assesses monitoring and detection gaps during the window and any unusual access attempts.
  • Reviews break-glass use for audit.
  • Checks whether the SSH bypass was used.
  • Preserves logs.

AWS Support & TAM Liaison

  • Opens a case on agent reconnection and endpoint behavior.
  • Asks about retry behavior and recommended steps.
  • Requests guidance on access alternatives.
  • Records guidance.

Business Continuity & Communications

  • Activates continuity for insurance operations and informs business owners about the patch window.
  • Issues time-stamped updates.
  • Coordinates manual workarounds.
  • Tracks the impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.8 vulnerability management, 8.32 change management; SOC 2 availability and security).
  • Assesses patch compliance deadlines.
  • Captures evidence of break-glass approvals.
  • Logs findings on change control.

Resilience Architect Guidance

Treat management connectivity as critical infrastructure. Use redundant VPC endpoints per AZ, canary instances that alarm on ConnectionLost, and staged changes to shared security groups.

Provide approved alternative access: EC2 Instance Connect Endpoint, serial console and a documented break-glass process with logging and approvals.

Make patching safe: maintenance windows with rate controls, halt conditions on failure rates, and ordering that protects databases.

Keep monitoring independent of a single path, and alarm on mass disconnection.

Auditors for ISO/IEC 27001:2022 (8.8, 8.32) and SOC 2 expect tested access alternatives, patch management evidence and change control.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on break-glass access and halt conditions for patching.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.

Hot wash questions

Use these with the full group of participants after the individual note-taking step.

  1. How quickly did you recognize the mass disconnection and why?
  2. How did you stop patching?
  3. How did you find half-patched servers?
  4. What break-glass access was used and who approved it?
  5. How did you fix the endpoint and handle drift?
  6. How did agent backoff affect recovery?
  7. How did you decide on the patch window?
  8. What security gaps appeared?
  9. How accurate were updates to leadership?
  10. What did AWS support add?
  11. What evidence did the scribe capture for auditors?
  12. What alternatives to SSM exist?
  13. What access or permissions were missing?
  14. What alarms are missing?
  15. What would you change in endpoint management?
