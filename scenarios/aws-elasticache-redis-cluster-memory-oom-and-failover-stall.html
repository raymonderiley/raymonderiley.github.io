AWS Elasticache Redis Cluster Memory OOM and Failover Stall

AWS Cloud Resiliency

Exercise Overview

This tabletop exercise examines an ElastiCache for Redis replication group that runs out of memory, evicts or rejects writes, and then stalls during failover because replicas have fallen behind. The database behind the cache takes the full read load, saturates, and the application suffers a cascading failure.

Participants are working-level: data platform engineers, application engineers, application owners, the service desk, cloud operations and monitoring staff, the AWS support liaison, business continuity coordinators and compliance staff. The exercise tests understanding of Redis memory policies, replication, failover behavior, cache stampede and fallback design.

A full run takes 3 to 4 hours, and the twelve-inject library supports repeated sessions. Inject #1 alone supports a 90-minute session.

Scenario

Lumen Retail uses a Redis cluster-mode-disabled replication group (one primary, two replicas) for product catalog caching, session storage and rate limiting. The node type is cache.r6g.xlarge with maxmemory-policy set to 'noeviction' because sessions must not be evicted. The primary database serves 5,000 requests per second at peak when the cache is cold.

At 11:00 on a flash sale day, a new feature stores large recommendation lists per user without TTLs. Memory climbs from 60 to 100 percent in 40 minutes. At 100 percent with noeviction, writes fail with 'OOM command not allowed', session creation stops and login failures begin. An operator triggers a manual failover to a replica, but the replicas are 800 MB behind and have the same memory problem. The failover stalls and the new primary also hits OOM minutes later.

What the team does not yet know: the recommendation feature has no TTL, the replicas lag because the output buffer limits are being hit, the application falls back to the database on cache errors without limiting concurrency so database load reaches 4x capacity, and the replacement node warm-up will take 15 minutes.

Exercise Objectives

  • Recognize Redis memory exhaustion. Participants read FreeableMemory, DatabaseMemoryUsagePercentage, Evictions, ReplicationLag and CPU to explain the failure.
  • Stabilize without making it worse. The team avoids repeated failovers, frees memory safely and handles the eviction policy trade-offs.
  • Protect the database. Engineers limit fallback traffic and prevent a cache stampede from collapsing the database.
  • Protect sessions and logins. Participants decide how to handle lost or failing sessions and user authentication.
  • Choose scale or fix. The team weighs scaling up, adding shards, deleting keys and fixing the feature.
  • Improve cache architecture. Participants review TTL discipline, memory alarms, eviction policy design and fallback behavior.
  • Communicate precisely and document for audit. Updates to leadership, site managers and users are accurate and time-stamped, and the evidence collected would satisfy ISO/IEC 27001:2022 incident management and SOC 2 availability reviewers.

Ground Rules

  • This is a discussion-based exercise. No production systems, accounts, configurations or backups will be touched. Commands and consoles are discussed, not executed.
  • Participants answer as they would in their real roles, using the runbooks, contact lists and tools that exist today. If a document or control does not exist, say so; that is a finding, not a failure.
  • Treat every inject as true unless the facilitator states otherwise. Do not argue the premise. Work the problem.
  • Time moves on the facilitator's clock. When an inject lands, the exercise clock is the time stated in the inject, regardless of how long discussion took.
  • Decisions must be stated aloud and recorded by the scribe with the decision maker's name and the exercise-clock time.
  • No blame. The exercise evaluates systems, process and documentation, not individuals.
  • Observers and evaluators record but do not answer questions for players unless the facilitator asks.
  • When discussing Redis actions, state the effect on memory, replication and sessions explicitly.

Exercise Timelines

Timeline and Escalation Triggers

T+00:00 — Detection and declaration. Login failures and OOM errors lead to declaration.

T+00:30 — Containment. The feature is disabled and fallback is limited.

T+01:15 — Diagnosis. Memory root cause and replication state are identified.

T+02:00 — Remediation planning. A memory relief and failover plan is agreed.

T+03:00 — Execution. Memory is freed or capacity added and failover is executed.

T+04:30 — Stabilization. Cache warms and the database load normalizes.

T+06:00 — Validation. Sessions and user flows are verified.

T+07:30 — Return to normal and close-out. Normal operation resumes and the incident is closed for debrief.

Injects

Inject #1: Redis OOM blocks logins and the failover stalls

Time frame T+00:00 · Variant Primary

Situation

It is 11:45. Customers cannot log in or add to cart during the flash sale. Application logs show 'OOM command not allowed when used memory > maxmemory'. CloudWatch shows DatabaseMemoryUsagePercentage at 100 percent and Evictions at zero because the policy is noeviction.

An operator triggered a failover 10 minutes ago. The replication group shows the new primary at 98 percent memory and replicas lagging. The database CPU is at 96 percent because cache misses and failures send every request to the database.

The recommendation feature released this morning stores per-user lists with no TTL. The AWS Health Dashboard shows no events. Marketing is about to send a second wave of sale emails.

Facilitator provides: the memory graphs, replication and parameter group details, database metrics and feature release notes.

Role actions

Incident Commander
  • Declare the incident and name the technical lead and scribe.
  • Decide whether to pause the sale emails.
  • Set the next update at T+00:20.
Data Platform Engineering (ElastiCache)
  • Explain the OOM and the stalled failover.
  • Plan immediate memory relief.
  • Plan safe failover timing.
Application Engineering
  • Disable the recommendation feature.
  • Limit database fallback concurrency.
  • Plan TTL and size limits.
Application Owners & Service Desk
  • Decide on session handling.
  • Service desk: issue the holding message.
  • Prepare a waiting room.
Cloud Operations & Monitoring
  • Build the dashboard.
  • Confirm alarms.
  • List missing alarms.
AWS Support & TAM Liaison
  • Open a case.
  • Ask about scaling options.
  • Record guidance.
Business Continuity & Communications
  • Inform marketing.
  • Prepare the first update.
  • Ask for documented RTO.
GRC, Audit & Compliance
  • Open the incident record.
  • Ask about the release review.
  • Start the evidence log.

Discussion questions

  1. Why does noeviction cause login failures at 100 percent memory?
  2. Why did the failover not fix the problem?
  3. How do you free memory safely and quickly?
  4. How do you protect the database from cache failures?
  5. What happens to sessions if you change the eviction policy or flush?
  6. Should you scale up the node or fix the feature first?
  7. Should the second sale wave go out?
  8. What do customers and marketing need to hear?

Facilitator notes

  • Do not reveal the missing TTL until ENG reviews the feature.
  • If players flush the cache, ask what happens to sessions and the database.
  • Look for the circuit breaker on database fallback.
  • Time-box to 35 minutes.

Roles and Responsibilities Summary

Incident Commander

  • Declares the incident, prioritizes login and checkout and decides on load shedding.
  • Runs a 20-minute cadence at first, assigns the scribe and records decisions.
  • Authorizes disabling the feature and accepting forced logouts.
  • Decides on sale restrictions.

Data Platform Engineering (ElastiCache)

  • Reads memory, eviction, replication lag and output buffer metrics.
  • Plans memory relief: delete or expire keys, scale up or add shards, adjust the eviction policy.
  • Plans failover timing and safety.
  • Reviews parameter group settings.

Application Engineering

  • Identifies the feature writing large keys without TTL and disables it by flag.
  • Adds a circuit breaker and concurrency limit on database fallback.
  • Implements TTLs and size limits.
  • Plans session fallback.

Application Owners & Service Desk

  • Application owners decide on session handling and acceptable degradation.
  • The service desk logs login complaints.
  • Owners prepare a waiting room for the sale.
  • Prepare validation tests.

Cloud Operations & Monitoring

  • Builds a dashboard of cache memory, replication lag, database load and login errors.
  • Confirms alarms.
  • Checks AWS Health.
  • Adds memory alarms.

AWS Support & TAM Liaison

  • Opens a case on replication lag and failover behavior.
  • Asks about scaling options and online resharding.
  • Requests guidance on output buffer settings.
  • Records guidance.

Business Continuity & Communications

  • Activates continuity for the flash sale and informs marketing.
  • Issues time-stamped updates.
  • Coordinates customer messages.
  • Tracks the impact.

GRC, Audit & Compliance

  • Ensures the incident is recorded and classified (ISO/IEC 27001:2022 5.24-5.28, 8.6 capacity management; SOC 2 availability).
  • Assesses customer and revenue impact.
  • Captures evidence of design gaps.
  • Logs findings on TTL and alarm gaps.

Resilience Architect Guidance

Separate data classes. Sessions that must not be evicted belong in a different cluster from disposable cache data, with the right maxmemory policy for each and TTLs on everything that can expire.

Alarm on memory and replication: DatabaseMemoryUsagePercentage, ReplicationLag and evictions, with thresholds well below 100 percent and runbooks for relief.

Protect the database: circuit breakers, concurrency limits, request coalescing and stale-while-revalidate behavior on cache failure.

Test failover under memory pressure and with lagging replicas, and size buffers and nodes with headroom.

Auditors for ISO/IEC 27001:2022 (8.6) and SOC 2 expect capacity management evidence, tested failover and monitoring.

Post-Exercise Debrief Guide

  1. Close the exercise formally. The facilitator announces the end of the exercise, reminds participants that all actions were simulated, and thanks the players. Nobody leaves before the hot wash.
  2. Take five minutes of silent individual notes. Each participant writes three things that worked, three that did not, and any gap in tools, access or documentation, before group discussion begins.
  3. Run the hot wash with the full group. Use the Hot wash questions below, going role by role for the first pass and then opening the floor. Keep to 45 to 60 minutes. Focus on memory relief choices and protecting the database.
  4. Hold evaluator readouts. Evaluators share timing observations, decision-log quality, communication accuracy and gaps against each objective.
  5. Prioritize findings. Group findings into people, process, technology and documentation, rate each by impact and effort, and select no more than ten for the corrective action plan.
  6. Assign corrective actions. Each action has an owner, a due date and a verification method. Record them in the GRC tracker as evidence for ISO/IEC 27001:2022 management review and SOC 2 reviews.
  7. Publish the after-action report within 10 business days. Include the timeline, decisions, findings, root causes, corrective actions and runbook updates, and circulate for review.
  8. Schedule the follow-up. Plan a validation drill in 90 days for the highest-priority gaps and rerun the exercise with different injects within 6 to 12 months.
